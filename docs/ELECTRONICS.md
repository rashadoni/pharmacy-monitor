# Профиль «электроника»: Kontakt Home, Irshad, Baku Electronics

Второй клиент того же продукта: **Kontakt Home** (kontakt.az) — клиент,
**Irshad** (irshad.az) и **Baku Electronics** (bakuelectronics.az) — конкуренты.
Решение владельца 2026-11-12.

## Как это будет жить рядом с аптеками

Не тенант в аптечной базе и не второй логин, а **отдельный экземпляр того же
кода**: своя база, свои юниты, свой адрес и вход. Причины — в коде, а не во
вкусе:

- товар в базе уникален по паре «сайт + идентификатор», без тенанта;
- список сайтов `pharmonline / aptekonline / aloe` прошит примерно в пятнадцати
  реестрах (`roi.ALL_SITES`, `product_policy.REQUIRED_CATALOG_SITES`,
  `storage.FULL_CATALOG_SITES`, `cadence`, …) и больше тысячи раз в коде;
- доверие ценам, рекомендации и health требуют свежего сбора **всех** сайтов из
  списка: упавший сбор электроники закрывал бы рекомендации аптечному клиенту;
- сопоставление товаров аптечное (доза, форма, страна); электронике нужно
  сопоставление по модели.

Экземпляр выбирает набор сайтов профилем. Профиль по умолчанию — аптеки:
аптечный прод работает как работал.

## Профиль экземпляра (шаг 2а)

Экземпляр выбирает набор сайтов переменной окружения `PM_PROFILE`:
`pharmacy` (по умолчанию, аптечный прод её не задаёт) или `electronics`.
Незнакомое имя — отказ при запуске, а не аптечный профиль: экземпляр
электроники с опечаткой не должен начать собирать аптечные сайты в свою базу.

Что профиль задаёт: сайты и их порядок (клиент первым), сайт клиента, подписи,
ритм сбора, сайты частичных тиков, сайты, чей каталог приходит файлом.
Реестры, объявленные константами модулей, читают это из `src/site_profile.py`: сборщики прогона
(`main.SCRAPER_CLASSES`), клиент и конкуренты в алертах, рекомендациях,
аналитике и отчёте, обязательные сайты доверия каталогу, ритм и все пороги
«данные устарели», сайты API, порядок колонок сравнения и Excel.

`tests/test_site_profile.py` запускает оба профиля отдельным процессом. Для
аптечного в тесте руками выписаны прежние значения реестров, объявленных
константами модулей, и он обязан дать их же; электроника — только свои три
сайта. Не закреплены тестом (сегодня совпадают с прежними — независимый разбор
запуском сверил их с кодом ветки `origin/main`, — но будущую поломку тест не
заметит): списки
сайтов внутри функций `health`, проверка сайта в ручной привязке по адресу,
четыре места старого Streamlit-дашборда, варианты `--site` у `alert add-rule`
и `ai-crawl`; тип значения (кортеж или список) и порядок ключей словарей,
например порядок `SCRAPER_CLASSES`, — сравнение идёт через JSON. Порядок
списков закреплён.

Растяжка в том же тесте роняет перечень аптечных сайтов, записанный в одну
строку кортежем, списком или множеством вне профиля; первым прогоном она нашла
шесть реестров, пропущенных при правке. **Она не гарантия:** словарь с
ключами-сайтами, многострочный список, значение по умолчанию
`client_site="pharmonline"` и сравнение `site == "pharmonline"` она не видит.

### Чего на этом шаге нет

⚠️ Экземпляр с `PM_PROFILE=electronics` ещё не рабочий, запускать его нельзя.
Переведены только списки-константы; ниже — что осталось прошитым под аптеки
(список составил независимый разбор чтением кода, 2026-11-13; строки могли
уехать, искать по тексту).

Упадёт сразу:

- `watchlist.categories_for_site` — разделы для сбора берутся из колонок
  `pharmonline_slug` / `aptekonline_slug` / `aloe_slug` таблицы `categories`;
  для сайта электроники `run` и `scrape` падают на `KeyError` (шаг 2б);
- значения по умолчанию `client_site="pharmonline"` у восьми ручек API —
  ответ 400, если интерфейс параметр не передал;
- словари «сайт → колонка слага» в API (фасеты товаров, страница категорий);
- назначение ручной категории в API (только товару pharmonline) — 404;
- `ai-crawl` неприменим: запасной обходчик написан только для аптечных сайтов,
  выбирать не из чего (так задумано).

Отработает молча и неверно:

- сравнение: провал в категорию ищет товар клиента как `site == "pharmonline"`
  (страница пустая), мёртвая ссылка клиента отбрасывается только для
  pharmonline, классификация категорий аптечная;
- Excel: заголовок «Позиция Pharmonline» на трёх языках — файл уходит клиенту;
- маржа и закупочные цены (`inventory.py`, план импорта в API) — ищут только
  товары pharmonline;
- прогноз (`forecast.py`) считает клиентом pharmonline;
- алерты в `api.py`: запасной сайт ссылки, сортировка «по сайту»; в
  `alerts.py` словарь цен матча заводит лишние ключи aptekonline и aloe
  (безвредно, но это реестр мимо профиля);
- `demo.py` молча пишет товары аптечных сайтов — не запускать;
- `intraday.py`: карта «сайт → колонка слага» знает только аптечные сайты.
  Пока у профиля электроники нет сайтов частичных тиков, не достигается; если
  их добавить, сайт молча сочтётся необслуживаемым;
- категории (`api.py`, `category_taxonomy.py`, `analytics.py`): создание
  связки пишет слаг только в аптечные колонки, счётчики отслеживаемых
  категорий дают нули, ярлыки собираются из аптечных колонок;
- закреплённые товары (`api.py`, `watchlist.py`) создаются со ссылками на три
  аптечных сайта; YAML-посев и CSV импорт/экспорт знают только аптечные
  колонки; сбор закреплённых ссылок (`main.collect_watchlist_urls`)
  перечисляет все сайты профиля, включая тот, чей каталог приходит файлом;
- `tenants.py` заводит арендатора `Default (pharmonline)` в любой базе;
- `validate-links` по умолчанию идёт на aptekonline;
- `url_parser.py` узнаёт адреса разделов только аптечных сайтов;
- старый Streamlit-дашборд — SQL и словари по аптечным сайтам;
- интерфейс: 71 строка с именами аптечных сайтов (шаг 4).

Сопоставление товаров аптечное (шаг 3). Ветки вида «если сайт aloe» и весь код
личностей pharmonline другому профилю не мешают.

### Ритм Kontakt Home — условный

В профиле у kontakt стоит 336 часов. Проверки двух других сайтов это не
ослабляет: срок жизни кэша рекомендаций станет 342 ч для всех, но при каждом
чтении заново идёт посайтовая проверка свежести (30 ч для суточных), остальные
пороги посайтовые. Для самого kontakt число условное:

- окно ритма — жёсткая двухнедельная сетка, а не возраст файла: файл,
  загруженный накануне границы окна, наутро считается просроченным, а
  загруженный сразу после — «свежим» 14 дней. Загрузке из файла (шаг 2в)
  нужно правило по возрасту последней загрузки;
- цена клиента до 14 суток считается текущей: алерты «конкурент дешевле» и
  рекомендации сравнивают свежие цены конкурентов с ценой клиента на дату
  файла. Это следствие того, что Kontakt Home приходит файлом;
- 14 дней — ещё и граница «цена устарела» на странице сравнения и «бренд
  активен» в аналитике: товары kontakt окажутся ровно на ней.

### К шагу 5 (сервер): что разбор сказал о переменной профиля

- **Опечатку защита ловит, отсутствие переменной — нет.** Команда экземпляра
  электроники, запущенная без `PM_PROFILE` (руками на сервере, юнит без файла
  окружения, шаг миграции в `deploy.yml`, который передаёт только
  `DATABASE_URL`), станет аптечной поверх базы электроники. До шага 5 нужна
  сверка «профиль ↔ база» при старте; метка `tenants.client_site` для неё не
  годится, пока арендатор по умолчанию везде создаётся с pharmonline.
- **`PM_PROFILE` задавать только в файле окружения systemd.** CLI читает `.env`
  рядом с кодом (и он перекрывает окружение), API под uvicorn `.env` не читает
  вовсе, Alembic и старый дашборд читают профиль раньше `.env`. Два экземпляра
  не должны делить один каталог кода с `.env`.
- **Мусор в значении роняет все юниты разом**, включая `health-check`:
  `PM_PROFILE=pharmacy # комментарий` (systemd хвостовой комментарий не
  срезает) — ошибка при импорте, тревогу поднять некому. На аптечном проде
  переменную не заводить; после правки файла окружения экземпляра электроники
  проверять запуском любой команды.
- Ручные workflow, которые кладут на сервер файлы поштучно
  (`category-hotfix-deploy.yml`, `health-pharmonline-hotfix-deploy.yml`), о
  новом `site_profile.py` не знают: `category-hotfix-deploy.yml`, запущенный с
  этого коммита на сервер со старым кодом, даст ошибку импорта (у него есть
  проверка и автооткат). Второй файл целиком не читали — его собственные
  проверки могут и так не пустить запуск. Обычный `deploy.yml` несёт весь `src`.

## Разделы сайтов и общий прогон (шаг 2б)

У аптечных сайтов разделы лежат в `categories` — по колонке на сайт. У сайтов
электроники разделов много, между сайтами они не совпадают и находит их сам
сборщик, поэтому у них своя таблица `site_routes` (миграция 0028): сайт,
раздел, включён ли, когда впервые и когда последний раз виден на сайте.
Аптечный экземпляр её не заполняет.

Список меняет только команда, а не каждый прогон — проверка полноты сверяет
прогон с запрошенными разделами, и знаменатель не должен меняться от ночи к
ночи:

    pharmacy-monitor routes sync --site bakuelectronics --dry-run   # что изменится
    pharmacy-monitor routes sync --site bakuelectronics             # записать
    pharmacy-monitor routes list --site bakuelectronics

`routes sync` обходит разделы на живом сайте (у Baku Electronics — через
прокси). Обход не удался — список не меняется. Раздел, пропавший с сайта,
выключается, а не удаляется; вернувшийся — включается той же строкой. Отказы:

- пустой список разделов не записывается никогда;
- если с сайта разом исчезло больше пятой части действующих разделов, запись
  идёт только с `--allow-shrink`: скорее обход прочитал не всё меню.

Прогон (`run --site irshad`) берёт включённые разделы сайта из этой таблицы
(`watchlist.categories_for_site`); аптечные сайты — из `categories`, как
раньше. Сайт без единого раздела сбор не проходит (`no_categories_configured`),
а не кончается «ok» с нулём товаров.

**База помечена профилем.** Арендатор по умолчанию заводится с клиентом из
профиля, и по этой метке отказывают `init_db` (его зовёт большинство команд
CLI), запуск API и команды, которые открывают базу мимо `init_db` — `rematch`,
`validate-links`, `report`, — если база принадлежит экземпляру другого
известного профиля: команда без
`PM_PROFILE` в каталоге экземпляра электроники — аптечная, и она не должна
начать собирать аптечные сайты в чужую базу. Отказ — только когда метка
называет сайт другого профиля; пустая метка, незнакомый сайт и недоступная
база экземпляр не останавливают (аптечную базу проверка остановить не может).
Оборотная сторона: если запрос метки не удался (сбой базы в эту секунду),
проверка пропускает. Команда, которая открывает базу мимо `init_db` и в список
выше не внесена, метку не сверяет — новой команде, которая пишет в базу,
добавлять `_refuse_foreign_database`.
⚠️ Метка появляется с первым `init_db`: пустую базу электроники первой должна
открыть команда с `PM_PROFILE=electronics`, иначе её пометит аптечный профиль.

`tests/test_electronics_instance.py` поднимает экземпляр отдельным процессом с
`PM_PROFILE=electronics` и своей базой и гонит настоящую команду `run` по трём
подставным сайтам: сбор, запись, проверка полноты, сопоставление, алерты,
отчёт, рекомендации.

Не сделано в этом шаге:

- Разделы Irshad пишутся первого уровня, как их отдаёт обход. При паузе 30 с
  большой раздел читается больше часа, и любой сдвиг списка за это время
  обнуляет проход — на живом полном сборе это ещё не проверено; если будет
  срываться, обход должен отдавать разделы второго уровня.
- `routes sync` на живом сайте командой ещё не запускался: обходы проверены
  пробой (`python -m src.scrapers.electronics --discover`), запись — тестами.
- Кнопка «Запустить scrape» одной категории (`--category-id`) сайтов
  электроники не касается: связки раздела с категорией у них нет.

## Каталог Kontakt Home из файла (шаг 2в)

Kontakt Home сборщиком не читается, поэтому его каталог приходит файлом,
который выгружает человек:

    pharmacy-monitor catalog import --site kontakt kontakt.xlsx --dry-run   # проверить файл
    pharmacy-monitor catalog import --site kontakt kontakt.xlsx             # загрузить

Принятый файл идёт тем же путём, что ночной сбор: полный прогон сайта с
записью цен, сопоставлением, алертами и рекомендациями (`src/catalog_file.py`
отдаёт файл прогону как сборщик с одним разделом). `--no-alerts` — загрузить
без рассылки алертов.

Формат — CSV (UTF-8) или XLSX с одним заполненным листом, с заголовком.
Колонки узнаются по названию на азербайджанском, русском или английском,
порядок любой:

- название и адрес страницы товара — обязательны;
- цена — обязательна как колонка; пустая у строки — товар без цены;
- цена со скидкой, старая цена, артикул, категория, наличие — если есть.

Действующая цена — цена со скидкой, если она названа, иначе цена. Скидкой это
считается, только когда рядом названа цена выше (старая или обычная). Старая
цена ниже действующей — подорожание: действующей она не становится.

Товар узнаётся по артикулу, а в строке без артикула — по адресу страницы
(вместе со строкой запроса).

Файл принимается целиком или отвергается со списком причин, и до записи дело
тогда не доходит:

- строка без названия или адреса, адрес не читается (и при заполненном
  артикуле тоже), цена не читается;
- два разных товара под одним идентификатором (одинаковая повторная строка
  отбрасывается и считается);
- две колонки на одну роль («Qiymət» и «price») — какая из них цена, не
  выбираем;
- незнакомая колонка, в названии которой есть слово «цена» («Kredit
  qiyməti»): в ней может лежать как раз действующая цена. Прочие незнакомые
  колонки не читаются и перечисляются в выводе команды;
- значение длиннее колонки базы; файл не в UTF-8; нечитаемый XLSX; данные
  на нескольких листах; ни у одного товара нет цены.

**Полнота файла.** Сколько товаров на сайте на самом деле, файл сказать не
может — раздел «файл» полон по определению, общая проверка полноты прогона
сверяет его с самим собой. Единственная мерка — прошлая принятая загрузка
этого же сайта (которой система поверила целиком): файл, в котором меньше 90%
её товаров, отвергается до записи. `--allow-shrink` — явное слово человека,
что каталог и правда сократился: оно снимает и это сравнение, и общие проверки
прогона на число товаров, так что файл принимается целиком, а не «прошёл
ворота и отвергнут дальше». ⚠️ Два ограничения:

- первую загрузку сравнить не с чем: обрезанный первый файл будет принят как
  полный каталог. Число товаров первого файла сверять с сайтом руками;
- мерка — прошлая загрузка, а не лучшая: файлы, каждый из которых на
  несколько процентов меньше предыдущего (100 → 91 → 82 → 74), проходят
  подряд. Смотреть число товаров в выводе команды.

Чего здесь нет и что важно знать:

- Какой файл даст выгрузка владельца, неизвестно: список названий колонок
  составлен наперёд. Нет обязательной колонки — отказ с перечнем найденных;
  добавить название — одна строка в `_COLUMN_ALIASES`.
- ⚠️ Идентификатор товара зависит от строки файла: есть артикул — артикул,
  нет — адрес страницы. Смена одного на другое между выгрузками заведёт
  товары заново, вторыми строками. То же случится, если Kontakt Home
  когда-нибудь откроют сборщику: он называет товар артикулом (`sku`). Выбрать
  один идентификатор до первой настоящей загрузки.
- Цена вида «849.990» читается как 849 990: точка с тремя цифрами после неё —
  разделитель тысяч. В XLSX цены приходят числами, и вопроса нет; в CSV —
  смотреть вывод `--dry-run` («цены: от … до …»).
- Товар, которого нет в новом файле, перестаёт обновляться, как товар,
  пропавший из листинга сайта; на живом экземпляре это не проверено.
- `--dry-run` с прошлой загрузкой не сравнивает.
- Свежесть: ритм kontakt в профиле условный (см. выше) — правило «устарел по
  возрасту загрузки» ещё не сделано.

## Сопоставление по модели (шаг 3, первая версия)

Аптечное сопоставление сверяет дозу, форму, фасовку и страну — товарам
электроники оно не подходит. У экземпляра электроники этап сопоставления
(`main._run_matching_stage`: конец прогона и команда `rematch` без флагов)
зовёт `src/electronics_matcher.py`. Флаги `rematch --reset`, `--revalidate`,
`--relink-dead`, `--threshold` — аптечные правила; у другого профиля команда
на них отказывает. Товар на разных сайтах узнаётся двумя способами:

- **по коду модели** — бренд и заводской код совпали («LG 55UR78006LK» и
  «Televizor LG 55UR78006LK 55" LED Smart TV»). Память и диагональ не должны
  спорить там, где названы у обоих. Остальные слова и цвет сверяются
  симметрично: лишнее у одной стороны — подробность её сайта, а когда у каждой
  стороны есть слово, которого нет у другой («i3» и «i5», «Lilac» и «Lemon»,
  «DOS» и «Windows», чёрный и белый), — это разные товары под одним кодом.
  Числа без букв и слова вроде «LED», «4K», «kq», «No Frost» при совпавшем
  коде не в счёт;
- **по линейке** — у телефонов кода в названии обычно нет: совпасть должны
  бренд, все слова модели, память, диагональ и цвет («Samsung Galaxy A55
  8/256GB Awesome Navy» у трёх сайтов записан по-разному, признаки одни).

Точность прежде охвата:

- чего название не говорит, то не додумывается: телефон с цветом и телефон без
  цвета по линейке парой не становятся; «iPhone 15» без памяти и цвета — не
  товар, а несколько товаров;
- оттенок и его слова — часть цвета: «navy» и «blue», «Light Blue» и «Blue»
  разные; чисто рекламные слова отбрасываются («Awesome Navy» = «Navy»);
- «+» в названии модели — слово «plus»: «S23+» и «S23» разные, «S23+» и
  «S23 Plus» — одно;
- характеристика — не код модели: процессор, ёмкость батареи, мощность, класс
  Wi-Fi, память, диапазон объектива остаются словами модели;
- по линейке «4K», «NFC», «Nano», «OLED», «Wi-Fi», «mouse» и «keyboard» —
  признаки товара, а не шум: «Mi TV Stick 4K» и «Mi TV Stick» разные;
- названия аксессуаров («çexol», «kabel», «üçün») — слова модели: чехол для
  телефона признаков телефона не получает;
- два равно подходящих товара одного сайта — неоднозначность: этот сайт в пару
  не входит ни при создании пары, ни при присоединении к готовой, ни на
  следующих прогонах;
- цены одного товара расходятся на проценты, а не в разы: пара с разницей
  больше 1,6 раза не создаётся;
- отказы оператора соблюдаются, ручные пары автомат не трогает; товар с мёртвой
  ссылкой новых пар не образует, но место своего сайта в готовой паре занимает;
- существующие пары не разбираются и не сливаются; новичок сверяется с каждым
  членом пары, и с пропавшим тоже.

Кандидаты ищутся по ключам (тот же код, те же признаки линейки), а не
перебором бренда: на каталоге в 10 тысяч товаров этап идёт секунды (есть тест).
Пары фиксируются внутри этапа, как у аптечного матчера: сбой алертов или
отчёта после него сопоставление не откатывает.

⚠️ Чего у первой версии нет:

- **Замера на живых каталогах.** Правила и словари (типы товаров, цвета,
  бренды, линейки, характеристики) написаны по образцам названий и по
  неверным парам, которые нашёл независимый разбор на придуманных, но
  правдоподобных названиях (они в тестах). Полных каталогов трёх сайтов в одной
  базе ещё не было: сколько товаров клиента получит пару и сколько пар неверны
  — неизвестно. Мерить после первого полного сбора экземпляра и первой
  загрузки файла Kontakt Home: выборка пар на глаз, как у аптечного матчера.
- Охват уступлен точности. По линейке пары не получит товар без узнаваемого
  бренда и товар, чьё название у сайтов отличается хоть словом: один дописал
  тип товара не из списка («Qulaqlıq … AirPods Pro 2»), назвал цвет или
  диагональ, которых нет у другого, написал «Onyx Black» против «Black»,
  «Wi-Fi» против «WiFi», «Watch6» против «Watch 6», «A55» против «A55 5G».
  Код модели, записанный через пробел («Beko WRE 6512 BWW»), кодом не
  узнаётся. По коду пары не будет, когда оба сайта дописали к нему разные
  незнакомые слова. Как часто это встречается на трёх сайтах — неизвестно.
- По коду товар без цвета сходится с товаром любого цвета, если на сайте он
  один такой: «Sony WH-1000XM5» и «…Black». Если это разные расцветки, пару
  снимает оператор.
- Правка правил к уже созданным парам сама не применяется: перепроверки
  существующих пар (как `revalidate_split` у аптек) нет.
- Штрихкодов сайты электроники не отдают; сопоставления по штрихкоду нет.
- Страницы ручного сопоставления интерфейса зовут аптечные правила
  (подсказки аналогов) — шаг 4.

## Сборщики

Все три читают сайт обычными HTTP-запросами, без браузера
(`src/scrapers/http_catalog.py`). Формы ответов сняты с живых сайтов 2026-11-12.

⚠️ **Kontakt Home сборщиком с сервера не читается (проба 2026-11-13).** Сайт
отвечает нашему сборщику проверкой Cloudflare («Just a moment»,
`cf-mitigated: challenge`) — и с адреса дата-центра, и через прокси Decodo.
Замерено: раздел каталога — отказ на всех десяти выходах прокси; главная и
`api.kontakt.az` — отказ на одном выходе каждая; выход прокси — азербайджанский
адрес (проверен один); `robots.txt` отдаётся. Вывод, а не замер: проверяется
клиент, а не адрес, — тот же сайт в обычном браузере открывается, а пробовали
мы один клиент (httpx); браузер через тот же прокси не пробовали. Обходить
проверку (подделка отпечатка браузера, решение задачи Cloudflare) не будем. Kontakt Home — клиент, и его цены берутся у
него самого: либо он разрешает адрес нашего сервера в своём Cloudflare, либо
отдаёт выгрузку каталога с ценами. Это вопрос владельца к клиенту. Сборщик
`kontakt.py` написан по формам, снятым в браузере, и остаётся для первого
варианта; до ответа клиента он не исполнялся ни разу.

| | Kontakt Home | Irshad | Baku Electronics |
|---|---|---|---|
| Имя сайта в коде | `kontakt` | `irshad` | `bakuelectronics` |
| Откуда каталог | `/<категория>.data` (данные витрины, turbo-stream) | `/az/list-products/<раздел>?page=N` (вёрстка карточек) | `/_next/data/<buildId>/az/catalog/<раздел>.json` |
| Товаров на страницу | 16 | 9 карточек | 18 |
| Сайт называет число товаров | да | нет | да |
| Идентификатор товара | `sku` (артикул) | номер товара на сайте | `product_code` |
| Наличие | признак «в наличии» | метка «Stokda var» | остаток числом |
| С адреса дата-центра | проверка Cloudflare (403) | открывается | блокировка Cloudflare (403) |
| Через прокси Decodo | та же проверка (403) | не нужен | открывается |
| Пауза между запросами | 2 с | 30 с (просит robots.txt) | 2 с |
| Страница на проводе | ≈23 КБ | ≈6 КБ | ≈12 КБ |

Что считается полным каталогом (`discover_categories`):

- **Kontakt Home** — все категории-списки (`type: CATEGORY`); сборщик находит
  их, спускаясь от меню сайта по витринам разделов (`type: SUBCATEGORY`).
- **Baku Electronics** — разделы верхнего уровня: список раздела включает
  товары всех подразделов (раздел tv-audio-video и объединение 19 его
  подразделов совпали товар в товар, 371 и 371). Раздел, чья страница на сайте
  сломана (telefonlar-qadcetler: 502 в браузере 2026-11-12, 301 через прокси
  2026-11-13), заменяется подразделами. Дерево разделов берётся из меню сайта —
  отдельного запроса к его API (`/megamenu`): в вёрстке главной ссылок на
  разделы нет, это показала первая же проба через прокси. **Полнота здесь —
  относительно меню:** раздел, которого в меню нет, обход не увидит и отказом
  не ответит; сверить меню не с чем. Что в меню не разобрано (ссылки не на
  разделы, группы без разделов), пишется в журнал событием
  `bakuelectronics_menu_read`. Ссылку верхнего уровня, чьё имя стоит в меню и
  как подраздел, обход проверяет у сайта: если её список товаров совпал со
  списком одноимённого подраздела (число товаров и коды первой страницы), это
  второй адрес подраздела, и верхним разделом она не считается
  (`bakuelectronics_menu_link_is_a_subsection`); не совпал или не прочитался —
  остаётся разделом: повтор товаров лучше потери раздела.
- **Irshad** — разделы первого уровня из меню (список foto-texnika совпал с
  объединением его подразделов, 16 и 16). Уценка и акции (`outlet`,
  `kampaniyalar`) не обходятся: это те же товары.

Проход категории цельный: неполный проход повторяется с начала, попытки не
склеиваются. Когда проход считается полным:

- **Kontakt Home и Baku Electronics** (сайт называет число товаров) — ни одной
  неразобранной записи, записей пришло ровно столько, сколько назвал сайт, и
  все они — разные товары. Это то же условие, что у проверки полноты прогона
  (`main._route_incomplete_causes`).
- **Irshad** (числа нет) — конец списка подтверждён двумя признаками сразу: на
  странице нет ссылки «показать ещё» **и** следующая страница пуста; нет
  неразобранных записей; ни одна карточка не пришла на двух страницах (иначе
  список сдвинулся посреди обхода). Не виден один случай: товар, снятый с
  сайта посреди обхода, сдвигает список без повтора, и соседний товар может не
  попасть ни на одну страницу.

Обход разделов (`discover_categories`) раздел, который не удалось прочитать, и
страницу незнакомого вида считает ошибкой, а не поводом вернуть список
покороче. Чего в меню сайта нет, он не видит вовсе — это граница правила у
всех трёх сайтов. У Baku Electronics есть ещё два места, где увиденная ссылка
в обход не попадает без отказа, только с записью в журнал: ссылка меню не на
раздел каталога и ссылка, которую сайт подтвердил вторым адресом подраздела. Проверка полноты прогона видит только запрошенные разделы, и
молча пропущенный раздел не числился бы пропущенным нигде.

Цена: товар без цены («по запросу», ноль) приходит с пустой ценой. У Irshad
запись, где есть зачёркнутая цена, а действующая не прочиталась, — отказ
записи: выдать зачёркнутую за действующую хуже, чем не выдать товар.

## К шагу 2: что разбор сказал об устройстве

- **Разделы не ложатся в нынешнюю таблицу.** У `categories` по одной колонке
  на аптечный сайт (`pharmonline_slug`, …), а у электроники разделов много на
  каждый сайт и между сайтами они не совпадают. Нужна своя таблица «сайт —
  раздел». Обход разделов (`discover_categories`) звать отдельной командой,
  которая пишет разделы в базу и показывает, что изменилось, — не в каждом
  прогоне: иначе знаменатель проверки полноты меняется от прогона к прогону, а
  у Kontakt Home это запрос через прокси на каждый узел дерева.
- **Разделы Irshad брать мельче.** Раздел первого уровня при паузе 30 с
  читается часами, а любой сдвиг списка за это время обнуляет проход.
- **Kontakt Home: родительский и вложенный список собираются оба.** Это лишние
  запросы через прокси, и категория товара — та, что записана последней.
  Решить по первому живому запуску.
- **Условие полноты записано дважды** — в `http_catalog.counted_pass_is_complete`
  и в `main._route_incomplete_causes`. Свести к одному.
- **Помощники Decodo** сборщики берут из `aptekonline.py`. Вынести в общий
  модуль первым коммитом шага 2.
- **Отслеживание отдельного товара по ссылке** (`scrape_product_page`) у этих
  сборщиков не написано: режим закреплённых ссылок вернёт пусто.
- **Нет остановки сайта целиком**, когда отказано во всех разделах подряд:
  сборщик обойдёт каждый раздел и получит отказ в каждом.
- Не проверено: есть ли у Irshad карточка, которую сайт повторяет на каждой
  странице (закреплённая, рекламная). Если есть, раздел с ней будет считаться
  сдвинувшимся всегда.
