## 🚀 Начальная настройка

### Запуск с нуля на чистой Ubuntu 22.04+

```bash
# 1. На локальной машине: запушить репозиторий в git
git push origin main

# 2. На свежем VPS:
ssh root@<vps-ip>

# 3. Запустить provision script
bash <(curl -fsSL https://raw.githubusercontent.com/USER/REPO/main/scripts/provision_vps.sh) \
  --repo https://github.com/USER/REPO.git \
  --domain monitor.pharmonline.az \
  --email admin@pharmonline.az \
  --dashboard-pass 'STRONG_RANDOM_PASS_16_CHARS_PLEASE'

# 4. Дописать .env (SMTP, Telegram, API key)
sudo -u pharmacy nano /opt/pharmacy-monitor/.env

# 5. Тест-прогон
sudo systemctl start pharmacy-monitor-run.service
sudo journalctl -u pharmacy-monitor-run -f

# 6. Проверка дашборда
# Открыть https://monitor.pharmonline.az в браузере с логином из шага 3
```

## 🔍 Диагностика

### Проверить состояние всех сервисов

```bash
systemctl list-timers 'pharmacy-monitor-*'
systemctl status pharmacy-monitor-dashboard.service
systemctl status pharmacy-monitor-telegram.service
```

### Проверить здоровье системы

```bash
sudo -u pharmacy /home/pharmacy/.local/bin/uv run \
  --directory /opt/pharmacy-monitor pharmacy-monitor health-check
```

Exit-code:
- `0` — OK
- `1` — warning
- `2` — critical (требуется вмешательство)

Health-email работает как состояние инцидента, даже если проверка запускается
каждый час:

- новая проблема или изменение набора/уровня проблем отправляется сразу;
- неизменившийся инцидент напоминается не чаще одного раза в 24 часа
  (`--alert-cooldown-hours` меняет интервал);
- первый успешный health-check после активного инцидента отправляет одно письмо
  `Pharmacy Monitor — RECOVERED`; следующие успешные проверки молчат;
- состояние хранится атомарно в `data/health_alert_state.json` (или в
  `HEALTH_ALERT_STATE_FILE`) и обновляется только после подтверждённой SMTP-отправки.

### Журнал API: строка запроса скрыта

uvicorn пишет в журнал `pharmacy-monitor-api` строку на каждый запрос. Всё после
`?` в адресе заменено меткой — в строке запроса ездит токен входа из письма:

```
INFO:     203.0.113.7:51324 - "GET /auth/verify?<hidden> HTTP/1.1" 303 See Other
```

Метод, путь и статус на месте; строка без `?` (`GET /health`) не меняется.
Делает это `src/access_log.py`, фильтр ставится при импорте `src.api` — юнит
для этого менять не нужно. Действует при обычном уровне журнала: с
`--log-level debug|trace` или `UVICORN_LOG_LEVEL` в окружении uvicorn печатает
запрос целиком, мимо фильтра.

**Нужны параметры запроса** (что клиент искал, с каким фильтром пришёл) — их
пишет Caddy, если на сервере у него включён журнал, как в `infra/Caddyfile`:
`journalctl -u caddy -o cat | grep /api/v1/dash/`. Значение параметра с именем,
похожим на секрет (`token`, `key`, `code`…), Caddy пишет как `<hidden>`, если на
сервере поставлен фильтр из образца — «Фильтр в журнале Caddy» ниже; без него
запрос с `?token=…` ложится в журнал целиком.

**Проверить после выкладки** (root). Запрос с параметром и его строка в журнале:

```bash
grep -c hide_query_strings /opt/pharmacy-monitor/src/api.py    # 0 — код не выложен
curl -s -o /dev/null -w '%{http_code}\n' 'http://127.0.0.1:8080/health?probe=1'   # ждём 200
journalctl -u pharmacy-monitor-api -n 20 --no-pager | grep 'GET /health'
journalctl -u pharmacy-monitor-api -n 60 --no-pager | grep -c 'probe=1'             # ждём 0
```

- `"GET /health?<hidden> HTTP/1.1" 200` и счётчик 0 — фильтр работает в
  запущенном процессе;
- строка с меткой есть, а счётчик не 0 — уровень журнала `trace`: uvicorn
  печатает запрос ещё раз, мимо фильтра. Уровень `debug` эта проверка не
  покажет — на нём целиком печатается только запрос на WebSocket; уровень
  смотреть прямо: `systemctl show -p Environment pharmacy-monitor-api` и
  `grep -c UVICORN_ /etc/pharmacy-monitor/env`;
- `"GET /health?probe=1 HTTP/1.1" 200` — процесс идёт без фильтра: API не
  рестартован после выкладки или выложена ветка, в которой правки нет;
- строки нет вовсе. Если curl ответил не 200 — строку вытеснила трассировка
  ошибки, смотреть окно шире (`-n 200`). Если 200 — uvicorn строк о запросах
  не пишет: журнал доступа выключен или уровень журнала `warning` и выше;
  скрывать тогда нечего, а юнит или окружение отличаются от репозитория:
  `systemctl cat pharmacy-monitor-api | grep -A7 ExecStart`.

Заодно — версия uvicorn (CI проверяет 0.46.0, руками проверена ещё 0.52.1) и не
терял ли фильтр записи:

```bash
/opt/pharmacy-monitor/.venv/bin/python -c 'import uvicorn; print(uvicorn.__version__)'
SINCE=$(systemctl show -p ActiveEnterTimestamp --value pharmacy-monitor-api)
journalctl -u pharmacy-monitor-api --since "$SINCE" | grep -c request_log_line_dropped   # ждём 0
```

Строки, записанные до рестарта, остаются в journald до ротации. Были ли они на
этом сервере вообще, покажет `journalctl -u pharmacy-monitor-api --since "30 days
ago" | grep -c 'HTTP/1\.[01]"'` (0 — журнал доступа не писался).

**В журнале `request_log_line_dropped`** — uvicorn сменил вид записи о запросе,
и фильтр перестал её узнавать. Запись, в которой он не может найти строку
запроса, не печатается; событие пишется один раз на логгер. Строк о запросах
в журнале API тогда нет — всех или только тех, что с параметрами. Запросы
видны в журнале Caddy; чинить — `src/access_log.py` и
`tests/test_access_log_carries_no_query.py` под новую версию uvicorn.

**Симптом:** последний прогон был >26 часов назад.

**Причины:**
1. Cron timer выключен → `systemctl status pharmacy-monitor-run.timer`
2. Сам прогон висит → `systemctl status pharmacy-monitor-run.service`

```bash

# Запустить ручной прогон
```

### В журнале сбора `incremental_persist_failed` или прогон `failed` с ошибкой базы

**Что это.** Полный сбор aptekonline (и pharmonline вне режима `public_api`)
пишет каждую категорию сразу после сбора, а в конце проходит по собранному ещё
раз. aloe и pharmonline в режиме `public_api` пишутся один раз, в конце. Строка
`incremental_persist_failed` значит, что запись одной категории не прошла.
Недописанное откатывается, сбор идёт дальше: следующие категории пишутся как
обычно, а финальный проход пишет всё ещё раз, включая отказанную.

- **Отказ был разовым** (оборванное соединение, блокировка) и пришёлся на запись
  категории — финальный проход её дописывает, прогон кончается как обычно.
  Ничего делать не надо.
- **Отказ повторился на финальном проходе** — база не принимает запись никогда
  (значение длиннее колонки, пустое обязательное поле) либо разовый сбой пришёлся
  на сам финальный проход. Прогон получает `failed` с причиной в
  `runs.error_message` и временем окончания. Финальный проход останавливается на
  отказанной пачке: в базе есть всё, что записано по категориям, и нет того, что
  мог записать только он, — остатка отказанной категории, разделов, оборвавшихся
  при сборе на середине, акций. У сайта без записи по категориям (aloe) не
  пишется и всё, что шло после отказанной пачки; если одной командой собирались
  несколько сайтов, то и сайты, стоявшие в финальном проходе после отказавшего
  (так читается код, прогоном не проверено). Сопоставление, алерты и
  рекомендации по этому прогону не считаются. Повтор — на следующем срабатывании
  таймера; запись, которую база не принимает, роняет сбор сайта каждый раз, пока
  её не исправят в сборщике (обрезать или отбросить значение).

**Смотреть:**
```bash
journalctl -u 'pharmacy-monitor-scrape@*' -o cat -g incremental_persist_failed | tail
sudo -u postgres psql -X pharmacy_monitor -c \
  "select id, status, finished_at, error_message from runs where status = 'failed' order by id desc limit 1"
```
В причине — класс ошибки, первая строка ответа базы и запрос без значений:
параметры и подробности (`DETAIL`) движок не печатает, они в журнале PostgreSQL
(«Параметры упавшего запроса» ниже). Колонку база называет не всегда: для
слишком длинной строки в причине остаются класс ошибки
(`StringDataRightTruncation`), код `SQLSTATE 22001` и запрос — какая из его
колонок не вместила значение, видно только в журнале PostgreSQL. Категория — в
строке `incremental_persist_failed`.

Перед записью итога обработчик сбоя откатывает транзакцию: то, что упавший шаг
успел отправить в базу и не зафиксировал, с итогом не сохраняется. Строки
журнала об этом:

- `persist_rollback_failed`, `run_failure_rollback_failed` — сам откат не
  прошёл; обычно это потерянное соединение, до сервера он не дошёл. Не
  отдельная поломка: сессия берёт новое соединение, причина сбоя остаётся
  прежней.
- `run_failure_write_retried` — первую запись итога база не приняла, вторая
  пишет итог один: статус, причину, время, у `run` — и заявку из очереди. Поля
  из `dropped_fields`, выставленные на прогоне перед сбоем (причина отказа
  проверки, `run_quality`), при этом не сохраняются; список бывает пуст — тогда
  первая попытка упала не из-за них.
- `run_failure_not_recorded` — не прошла и вторая попытка. Прогон остаётся
  `running`. Почему он упал — в выводе команды (строка `Error: …`), а у `run`
  ещё и в строке `run_failed` выше, с трассировкой. Дальше — как с любым
  зависшим прогоном, см. ниже.

То же относится к `scrape` (его зовут intraday-тики) и `ai-crawl`: после сбоя
базы прогон закрывается как `failed` с причиной. `watchlist-tick` идёт через
`run`.

**До этой правки** (выложено ли — `grep -c _persist_chunks
/opt/pharmacy-monitor/src/main.py`, 0 — нет) тот же сбой выглядел иначе: все
категории после отказанной терялись (`incremental_persist_failed` на каждой — с
`PendingRollbackError` или `InFailedSqlTransaction`), обработчик сбоя падал на
собственном commit, и итог не записывался.

**Прогон висит `running`, а процесса сбора нет.** Так кончается сбор, который
убили (перезагрузка, `TimeoutStartSec`, Ctrl-C), у которого база не приняла и
запись итога, а до правки выше — любой сбой базы посреди записи. Пока строка
висит:

- запуску планового сбора она не мешает: гвард ритма читает только
  завершившиеся попытки, сайт остаётся «не собран» и собирается на следующем
  срабатывании таймера (у aptekonline — через неделю);
  (⚠️ Уточнение 2026-10-14: с этого дня сбор на сервере ежедневный у всех трёх
  сайтов — следующее срабатывание таймера это ближайший будильник, 01:00 или
  03:15 по хосту; «через неделю» больше ни у кого нет. Раздел «Ежедневный сбор:
  что стоит на сервере».)
- **итогу сбора другого сайта — мешает.** Если висит полный сбор одного сайта, а
  у всех трёх есть свежий проверенный каталог, проверенный сбор другого сайта
  сам кончается `failed` на пересчёте рекомендаций (`ROI refresh failed for
  trusted epoch: …`), а кэш рекомендаций удаляется. Товары и цены соседа к этому
  моменту записаны, но проверенным его сбор не считается. Все три сайта
  собираются в ночь на понедельник с разницей в час-два, то есть внутри шести
  часов до вотчера; повтор у aloe и pharmonline — следующей ночью, у
  aptekonline — через неделю;
  (⚠️ Уточнение 2026-10-14: после перехода на ежедневный сбор неверно. Три сайта
  стартуют каждую ночь в 01:00 по хосту и идут очередью около 70 минут, повтор
  неудачного — в 03:15; всё это внутри шести часов до вотчера, только теперь
  каждую ночь, а не в ночь на понедельник. Повтор соседа в 03:15 тоже внутри
  этих шести часов: по коду проверенные цены он вернёт, только если у
  зависшего сайта к тому времени есть более новая попытка, а рекомендаций нет,
  пока строку не закрыл вотчер (`has_unfinished_run`, пункт ниже). Прогоном не
  проверено.)
- health её не видит и `last_run_failed` не поднимает — он смотрит на последний
  завершившийся прогон. Тревога придёт только по возрасту прежнего каталога
  (`full_catalog_overdue`, `stale_run`), без причины;
- рекомендации не считаются (`roi_compute_run_in_progress`), `alert evaluate`
  без номера прогона ничего не выдаёт, у сайта нет сбора, которому система
  верит.

Закрывает её вотчер очереди: раз в минуту, когда нет процесса сбора, он зовёт
`reap-stale-runs`, и прогон старше шести часов (`SCRAPE_MAX_HOURS`) получает
`failed` задним числом — `finished_at` равен `started_at`, вместо причины
пометка `reaped stale`. Работает ли вотчер и есть ли такие строки:

```bash
systemctl is-active pharmacy-monitor-scrape-watcher.timer
sudo -u postgres psql -X pharmacy_monitor -c \
  "select id, status, started_at, full_catalog_sites from runs where finished_at is null"
```

Не ждать шесть часов — та же команда руками, под `pm` с загруженным env.
Сначала убедиться, что процесса сбора нет: команда откажет, пока замок сбора
занят, но сбор, потерявший соединение замка (перезапуск PostgreSQL), она за
живой не примет. Первая команда должна ничего не напечатать (еженедельный сбор
pharmonline запущен как `python -m src.main run`, поэтому имён два):

```bash
pgrep -af '(pharmacy-monitor|src\.main)( --log-level [A-Za-z]+)? (run|scrape|intraday-tick|watchlist-tick|rematch|ai-crawl)( |$)'
.venv/bin/pharmacy-monitor reap-stale-runs --max-age-hours 0 --reason "<что случилось>"
```

Workflow `recover-interrupted-empty-run.yml` для этого не годится: он закрывает
только пустой полный прогон pharmonline (ни одного товара и ни одной цены).

Замер на проде 2026-10-13 (чтение): незакрытых прогонов нет; последние прогоны
с пометкой `reaped` начаты 9 июля 2026; вотчер включён, в его скрипте вызов
`reap-stale-runs` есть; в журнале PostgreSQL за всё время, что он хранится
(семь файлов, самый ранний закрыт 6 сентября), нет ни одной строки `current
transaction is aborted`; в журнале сервисов сбора, тиков и вотчера за 40 дней —
ни `InFailedSqlTransaction`, ни `PendingRollbackError`.

### Email не приходит

**Симптом:** получатель не получил письмо — о прогоне, дайджест, ссылку на вход.

Адресов в журнале нет: получатель назван `user_id`, ошибка — классом и кодом
ответа SMTP. Почему так — ниже, «Адреса в журнал не пишутся».

Если письмо о прогоне не приходит сотруднику клиента — сначала «Email —
слишком много писем» → «Клиенту мгновенные письма не идут»: с 2026-10-13 это
намеренно, настройкой получателя.

**1. Что сказал журнал.** Где он лежит, зависит от того, кто слал:

- плановые сборы — `journalctl -u 'pharmacy-monitor-scrape@*' --since '2 days ago'`;
- еженедельный сбор pharmonline — журнал шага GitHub Actions, `gh run view <id> --log`;
- письмо админу с тика — `-u pharmacy-monitor-intraday`;
- недельный дайджест — `-u pharmacy-monitor-digest-weekly`;
- утреннее письмо с разницей цен — `-u pharmacy-monitor-digest-daily` (разбор его
  событий — «Утреннее письмо с разницей цен»);
- письмо о здоровье — `-u pharmacy-monitor-health`;
- ссылка на вход — `-u pharmacy-monitor-api`.

| В журнале | Что значит |
|---|---|
| `smtp_send recipients=N`, следом `smtp_sent_ok` | Почтовый сервер письмо принял. Дальше — не у нас: доставку смотреть в кабинете Resend |
| `…_failed user_id=… error_type=…` | Не ушло; причина — в `error_type`, таблица ниже. События: `email_batch_failed` (письмо о прогоне и письмо админу с тика), `digest_email_failed`, `login_link_email_failed`, `email_dispatch_failed`, `alert_email_failed`, `error_email_failed`, `pharmonline_admission_mail_failed` (письмо админу о товарах, которые сбор pharmonline допустил сам). Строки `smtp_send` перед ним может и не быть: до разговора с сервером дело не дошло |
| `email_skipped_no_smtp` | В окружении нет `SMTP_HOST` — обычно ручной запуск без загруженного env |
| Нет ни `smtp_send`, ни `…_failed` | Письмо и не собирались слать: нет событий, порог важности получателя, включённый `daily_digest`, запуск с `--no-alerts` |

**2. Что значит `error_type`.** Рядом с ним — числа, по которым случаи
различаются: `smtp_code` (ответ сервера, 550), `smtp_status` (уточнение из того
же ответа, `5.1.1`), у сетевых ошибок — `errno`.

| `error_type` | Причина |
|---|---|
| `SMTPAuthenticationError` (535) | Не подходят `SMTP_USER` / `SMTP_PASSWORD` — ключ отозван или заменён |
| `SMTPSenderRefused` | Сервер не принял отправителя: `SMTP_FROM`, домен не подтверждён |
| `SMTPRecipientsRefused` | Сервер отказал в адресе получателя (`5.1.1` — такого ящика нет) — проверить адрес у пользователя `user_id` |
| `SMTPDataError` | Письмо отклонено целиком: размер, лимит отправки, содержимое |
| `SMTPServerDisconnected`, `TimeoutError`, `ConnectionRefusedError`, `gaierror`, `OSError` | Почтовый сервер недоступен или сеть |
| `KeyError` | В окружении нет `SMTP_USER` или `SMTP_PASSWORD` |
| `ValueError` | Некому слать: получатели не заданы |

**3. Кто такой `user_id`** — на сервере (адрес остаётся в терминале оператора):

```bash
sudo -u postgres psql -X pharmacy_monitor -c \
  "select id, email, role, is_active, email_severity_min, daily_digest, weekly_digest
   from tenant_users where id = <user_id>;"
```

**4. Полный ответ сервера** в журнал не пишется. Его печатает проверка доставки,
которую запускают руками:

```bash
# на сервере, под pm, с загруженным env
set -a; source /etc/pharmacy-monitor/env; set +a
.venv/bin/pharmacy-monitor notify test --email <свой адрес>
# email:    FAIL — SMTPDataError (SMTP 554 5.7.1): <ответ сервера, адреса вырезаны>
```

Проверка воспроизводит только отказ, который повторяется. От разового сбоя
остаются класс ошибки и коды в журнале.

Без `--email` тестовое письмо уйдёт по старому списку: таблица `recipients`, а
если она пуста — `EMAIL_TO`.

#### Адреса в журнал не пишутся

Репозиторий публичный, и журнал шага GitHub Actions читает любой пользователь
GitHub; хранится он 90 дней. Еженедельный сбор pharmonline идёт оттуда и
рассылает письма о прогоне — всё, что команда печатает, оказывается в этом
журнале. Получатели — администратор и сотрудник клиента.

- Вызов журнала не получает ни адрес, ни Telegram-идентификатор: пишется
  `user_id` или число получателей.
- Текст ошибки отправки в журнал не идёт — smtplib кладёт адрес и в него.
  Пишутся класс ошибки и код ответа: `**notifier.delivery_error_fields(exc)`.
  Отказ SMTP выходит из `notifier.send_email` как `EmailDeliveryError` уже без
  адреса в тексте — на случай, если ошибку поймают выше и напечатают целиком.
- Вывод журнала CLI вырезает из готовой строки всё, что похоже на адрес
  (`logging_setup.masking`), — последняя линия, а не разрешение писать адреса и
  не защита секретов: шаблон простой, адрес необычной записи он вырежет не
  целиком. Заодно под него попадает и не-адрес той же формы, например имя юнита
  `…@….service`.

Возврат ловит `tests/test_log_carries_no_address.py`: читает в `src/` вызовы
журнала, `print` и `click.echo` и зовёт почтовые пути, у которых есть свой
обработчик сбоя. Маска стоит только на журнале CLI. Мимо неё идут `click.echo`
и `print`, а журнал API не замаскирован вовсе — он пишет в journald и наружу не
выходит. Команды, которые печатают адрес по назначению, перечислены в том же
тесте (`recipient …`, `tenant add-user`, `tenant issue-token` — последняя
печатает ещё и токен входа), и он же следит, чтобы ни один workflow их не
запускал. `telegram poll` печатает имена и идентификаторы из Telegram — тоже
только руками.

Если адрес в журнал Actions всё же попал — журнал прогона удаляется целиком,
необратимо и только по слову владельца:

```bash
# сначала убедиться, что это тот прогон: строки журнала команды с адресом
gh run view <id> --log | grep -E 'recipients=|user=|email=' | grep -c '@'
gh api -X DELETE repos/rashadoni/pharmacy-monitor/actions/runs/<id>/logs
```

### Ссылка из письма не входит

**Симптом.** Тексты на страницах — на азербайджанском и русском: язык того, кто
ещё не вошёл, неизвестен.

- По ссылке на вход открывается страница с кнопкой «Daxil ol / Войти». Вход
  происходит по нажатию: сама страница токен не шлёт (ссылку открывают и
  проверки ссылок в почте — такая проверка погасила бы её раньше человека).
- После нажатия — «Keçid etibarsızdır və ya artıq istifadə olunub / Ссылка
  недействительна или уже использована»: отказ. Ссылка истекла, по ней уже
  вошли, её погасила более новая. Кнопка «Davam edin / Продолжить» ведёт в
  дашборд, а если входа нет — на страницу входа; появляется она через
  секунду после отказа, чтобы второе нажатие «Войти» на неё не попало.
- Сразу, без кнопки входа, — «Keçid natamamdır… / Ссылка неполная. Откройте её
  из письма ещё раз»: в адресе нет части после «#» (ссылку набрали руками,
  скопировали не целиком, почтовый шлюз обрезал её).
- «Keçidi yoxlamaq alınmadı. Yenidən cəhd edin / Не удалось проверить ссылку.
  Попробуйте ещё раз» — не отказ: сеть, перезапуск API, ответ 5xx, нет ответа
  30 секунд. Повторное нажатие или обновление страницы повторяют попытку.
  Ссылка цела, кроме одного случая: сервер вошёл, а ответ до страницы не
  дошёл — тогда повтор скажет «уже использована», и нужна новая ссылка.
- Форма создания пароля после отправки пишет «Link yararsız və ya müddəti bitib»
  («Ссылка недействительна или истекла») либо сразу показывает «Məktubdakı linki
  yenidən açın. Alınmasa, administratordan yeni link istəyin» («Откройте ссылку
  из письма ещё раз. Не помогло — попросите администратора выслать новую»):
  токена у формы нет — её открыли не по ссылке из письма, в другом браузере или
  вкладке, либо письмо старого образца.
- Адрес `/login?error=link` без сообщения — так отвечает только прежний путь,
  `GET /auth/verify?token=…` (письмо старого образца, скрипт).

Ссылка живёт 30 минут и входит один раз; новая ссылка тому же пользователю гасит
прежнюю. Ссылки, выданные до выкладки правки от 2026-10-10, не действуют вовсе.

«Один раз» — и для одновременных запросов: гашение — один UPDATE с условием
(`tenants.redeem_magic_token`), из двух запросов с одним токеном проходит один,
второй ждёт его транзакцию и получает отказ. До второй правки от 2026-10-10
проходили оба, а у формы создания пароля оставался пароль того, кто записал
последним.

**Ссылку гасит только то, ради чего её предъявили.** Вход и запись пароля идут
одной транзакцией с гашением:

- форма пишет «Пароль слишком длинный…», «Минимум 6 символов» или «В пароле
  есть знак, который нельзя сохранить» — страница не отправила запрос, а если
  отправила, сервер ответил 422 раньше, чем дошёл до токена. Ссылка цела, пароль
  набирают заново на той же странице. Предел — 72 байта (столько берёт bcrypt):
  72 латинских знака, 36 кириллических; буквы вроде ə, ö, ş тоже занимают по
  два. Пробелы по краям пароля не считаются и не сохраняются — вход их
  отбрасывает тоже;
- ответ 500 при создании пароля или входе по ссылке — сбой случился до записи,
  транзакция откатилась, ссылка цела: после устранения причины та же ссылка
  работает, пока не вышли её 30 минут. После записи остаётся только выдача
  ответа; если сорвалась она, ссылка погашена, а пароль уже задан — входить
  паролем;
- гаснет без пароля ссылка в одном случае: её отправили в форму создания пароля,
  а пароль у пользователя уже есть (ответ 400 «Пароль уже задан»). Так было и
  раньше.

До этой правки пароль длиннее 72 байт (73 латинских знака или 37 кириллических
при разрешённых 200) сжигал приглашение: токен гас отдельной записью, потом
bcrypt 5 падал, ответ 500, пароля нет. Смена пароля в дашборде и вход с таким
паролем тоже отвечали 500; теперь это отказ (422 и «неверный пароль»).

**«Пароль задан, а не входит».** До этой правки пароль сохранялся как набран, а
вход отбрасывал пробелы по краям: пароль с пробелом в начале или в конце
задавался, но не входил никогда. По хешу такой пароль не отличить. Пользователь
входит по ссылке («Отправить ссылку») и меняет пароль в настройках, набрав
текущий в точности как задавал — с пробелами; новый сохранится уже без них.

Если он не помнит, как именно набирал, сам пароль не сменит: настройки требуют
текущий, а форма создания пароля при заданном пароле отвечает «Пароль уже
задан». Сброса пароля в приложении нет. Остаётся стереть пароль в базе — запись
в боевую базу, только по слову владельца — и выслать ссылку: пользователю без
пароля она ведёт на создание пароля.

```sql
update tenant_users set password_hash = null where id = <id>;
```

Первому администратору так делать нельзя, пока в `/etc/pharmacy-monitor/env`
задан `ADMIN_PASSWORD_HASH`: без своего пароля вход логином `admin` снова примет
общий пароль из env.

**В базе ссылки нет.** Там лежит SHA-256 токена (`tenant_users.magic_token`):
содержимое колонки по ссылке не входит, и ссылку из него не восстановить.
Пользователю высылают новую — «Отправить ссылку» на странице «Пользователи» или
`POST /auth/request`. Письмо не пришло — раздел выше, событие
`login_link_email_failed`.

**До сервера токен доходит только телом запроса (2026-10-12).** Адрес в письме —
`…/auth/link#token=…` (вход) или `…/auth/link/password#token=…` (создание пароля).
Часть адреса после «#» браузер серверу не отправляет: её нет ни в запросе
страницы, ни в заголовке Referer. Обе страницы отдаёт API (`src/login_link_pages.py`),
а не фронтенд:

- вход — страница показывает кнопку и по нажатию шлёт токен телом
  `POST /auth/verify`, затем уходит на `/overview`;
- создание пароля — страница кладёт токен в хранилище вкладки (`sessionStorage`)
  и уходит на форму `/set-password` по чистому адресу; форма берёт токен оттуда и
  шлёт телом `POST /auth/set-password`. Токен, по которому задан пароль или
  сервер отказал как по ссылке (ответы 401 и 400), форма из хранилища стирает.

Тело запроса ни Caddy, ни журнал доступа API не пишут. Caddyfile и юнит API не
менялись — руками на сервер ставить нечего, правка доезжает обычной выкладкой,
миграций в ней нет. Нужно от Caddy одно — чтобы `/auth/*` шло в API; так и есть:
2026-10-12 `GET https://leaddrive.cloud/auth/verify` без токена отвечает 422 от
FastAPI.

Почему страницу отдаёт не фронтенд. Next.js кладёт адрес своей страницы вместе с
частью после «#» в заголовок `Next-Router-State-Tree`, а заголовки запроса Caddy
пишет в журнал. 2026-10-10 на проде токен единственной открытой с 3 сентября
ссылки (6 октября, создание пароля) лежал в 41 записи Caddy, в четырёх полях:
`Referer` запросов со страницы (35 записей), адрес (6), `Location` редиректа с
`/set-password` на `/az/set-password` (3) и `Next-Router-State-Tree` (1). Пока
пароль не задан, такая запись была рабочей ссылкой: страницу отдаёт фронтенд,
токен при этом не гаснет. **Адрес с токеном — в любом виде — странице Next не
давать.** Что браузер отправляет на самом деле, проверяет настоящий Chromium:
`tests/test_login_link_in_a_browser.py`.

Фильтр в журнале Caddy эту правку не заменяет — он второй слой, и на сервере
его ставят отдельно: «Фильтр в журнале Caddy» ниже. Он вырезает значение из
перечисленных полей, а четвёртое поле (заголовок Next) до замера 2026-10-10
никто бы не перечислил.

Проверить на сервере (только чтение). Выслать себе ссылку («Отправить ссылку» на
странице «Пользователи»), открыть её, затем искать в журналах сам токен — часть
ссылки после `#token=`. Он вводится без показа на экране и в историю команд не
попадает:

```bash
read -rs -p 'токен из ссылки: ' T; echo
journalctl -u caddy -u pharmacy-monitor-api --since '-1 hour' -o cat | grep -c -F -- "$T"   # 0
grep -c -F -- "$T" /var/log/syslog                                                         # 0
unset T
```

Искать по слову `token=` недостаточно: в заголовке Next адрес закодирован
(`%23token%3D…`), а сканеры ходят по чужим адресам со своим `token=` (2026-10-10 —
8 таких строк, `/v1/onboarding/config`). Токен состоит из знаков, которые
кодирование не меняет, поэтому поиск по значению находит его в любом поле.

Выложено ли — смотреть и API, и фронтенд: ссылку на создание пароля доводит до
конца только новая форма.

```bash
ls /opt/pharmacy-monitor/src/login_link_pages.py /opt/pharmacy-monitor/frontend/src/lib/link-token.ts
systemctl show pharmacy-monitor-api pharmacy-monitor-frontend -p ActiveEnterTimestamp
curl -s -o /dev/null -w '%{http_code}\n' https://leaddrive.cloud/auth/link    # 200; до выкладки — 404
```

**Новый API при прежнем фронтенде.** Выкладка перезапускает оба сервиса подряд,
после сборки фронтенда; если сборка упала, не перезапущен ни один. Но новый
`src/` уже лежит на диске, и любой перезапуск API (сбой, перезагрузка сервера,
рестарт руками) поднимет новый код рядом со старой формой. Ссылки на вход тогда
работают — фронтенд им не нужен; ссылка на создание пароля приводит на прежнюю
форму, и та после отправки пишет прежний текст «Linkdə token yoxdur». Токен при
этом цел:
довести выкладку и открыть ту же ссылку ещё раз, пока не вышли её 30 минут.
При откате кода ссылки, выданные новым кодом, ведут на адрес, которого у
прежнего API нет (404), — их высылают заново.

**Письма, полученные до выкладки** — и выданные, пока она шла: до перезапуска
API работает прежний код, а сборка фронтенда занимает минуты. Ссылка на
создание пароля (`/set-password?token=…`) открывает форму с текстом «Məktubdakı
linki yenidən açın…»: из адреса форма токен больше не берёт. ⚠️ Адрес такой
ссылки Caddy запишет, как раньше, а токен при этом не гаснет — запись остаётся
рабочей ссылкой, пока не вышли её 30 минут. Пользователю высылают новую
(«Отправить ссылку»): она гасит прежнюю сразу. Чтобы этого не понадобилось, не
выкладывать в полчаса после отправки приглашения. Вкладка с
формой, открытая до выкладки, пароль задаст: её код токен уже прочитал и шлёт
его телом, как раньше. Ссылка на вход (`/auth/verify?token=…`) идёт прежним
путём и входит, если токен ещё жив. Её адрес Caddy запишет; после входа токен
в записи погашен, а после сбоя (ответ 5xx) остаётся рабочим, пока не выйдут его
30 минут.

**Что осталось в журналах от прежних ссылок.** Записи с токеном правка не
стирает: в журнале systemd срок хранения не задан (2026-10-10 он лежит с
3 сентября, 1,5 ГБ; старое вытесняется по объёму), копия тех же строк —
в `/var/log/syslog*`, там четыре недельных файла. Читают оба root и группа `adm`;
`pm`, под которым ходит CI, не читает. Токен в них мёртв: срок 30 минут вышел,
пароль по нему задан, живых ссылок в базе 2026-10-10 не было. Чистить журнал ради
него не нужно — `journalctl --vacuum-*` стирает журнал всех служб.

**Страница пишет «Слишком много попыток. Подождите минуту и попробуйте ещё раз»**
(«Həddindən çox cəhd edildi…»). Это ответ 429 от счётчика попыток входа по
ссылке (2026-10-12): с одного адреса до проверки токена доходит десять попыток в
минуту, считая удачные. Сервер ссылку при этом не проверял и не гасил: через
минуту нажатие «Войти» входит — или страница пишет, что ссылка не годится.
Отклонённая попытка в счёт не идёт: тот, кто жмёт кнопку раз за разом, срок
себе не продлевает. Адрес — тот, с которого клиент выходит в интернет: офис за
одним адресом делит счётчик на всех, и десять запросов в минуту оттуда закрывают
вход по ссылке всему офису на эту минуту. Вход по паролю считается отдельно и
при этом работает.

Кто и сколько — по журналу доступа API (адрес клиента в нём есть, строки
запроса нет; включён ли журнал доступа на сервере, на 2026-10-12 не выяснено —
пустой вывод может значить и это):

```bash
journalctl -u pharmacy-monitor-api --since '-10 min' -o cat \
  | grep -oE '[^ ]+ - "(GET|POST) /auth/verify[^"]*" [0-9]{3}' \
  | sed -E 's/:[0-9]+ - / /' | sort | uniq -c | sort -rn | head
```

Десятки строк с одного адреса с ответами 401 и 429 — кто-то перебирает токены;
до базы из них доходит десять в минуту. Счётчик лежит в Redis под именем
`ratelimit:verify:<адрес>` (в имени адрес клиента, токена там нет) и сам
пропадает через две минуты после последней попытки с этого адреса, принятой или
нет, — снимать его руками незачем. Если `REDIS_URL` на сервере не задан,
счётчик держит каждый рабочий процесс API сам: их два, и предел выходит до
двадцати попыток в минуту. 2026-10-12 задан (`grep -c '^REDIS_URL='
/etc/pharmacy-monitor/env` дал 1), и `/health` отдаёт в `redis_ping_ms` число
(3–7 мс; без Redis там `null`) — Redis процессу API отвечает.

У всех клиентов сразу 429 при первой же попытке — счётчик стал общим: API видит
вместо адреса клиента адрес прокси. Смотреть адреса в журнале API командой
выше: если там у всех `127.0.0.1`, заголовок `X-Forwarded-For` до API не доходит
или ему не верят. Адрес клиента uvicorn берёт из этого заголовка, когда запрос
пришёл с доверенного адреса; доверенный — 127.0.0.1, так и по умолчанию, и
флагами юнита (`systemctl cat pharmacy-monitor-api | grep -A6 ExecStart`:
`--proxy-headers`, `--forwarded-allow-ips '127.0.0.1'`). Ломают это
`--no-proxy-headers`, переменная `FORWARDED_ALLOW_IPS` в
`/etc/pharmacy-monitor/env` при юните без флага, Caddy на другой машине или в
контейнере, unix-сокет. 2026-10-12 живой юнит прочитан: оба флага на месте,
`FORWARDED_ALLOW_IPS` в окружении нет. Выкладка юниты не ставит — после правки
`ExecStart` руками команду повторить.

Выложена ли правка: `grep -c 'verify:{client_ip}' /opt/pharmacy-monitor/src/api.py`
(0 — нет) и время старта процесса, как ниже. 2026-10-12 выложена (API поднялся в
11:06 по времени сервера).

Проверить счётчик на живом сайте — с машины, чей вход по ссылке на минуту не
жалко: с её адреса он на эту минуту закрыт. Токены неверные, в базе ничего не
меняется:

```bash
for n in $(seq 1 12); do
  curl -s -o /dev/null -w '%{http_code} ' -X POST https://leaddrive.cloud/auth/verify \
    -H 'Content-Type: application/json' -d "{\"token\":\"rate-limit-check-$n\"}"
done; echo
```

Ждём десять `401` и два `429` — если за последнюю минуту попыток с этого адреса
не было; иначе `401` выйдет меньше. 2026-10-12 с dev-бокса так и вышло (22 запроса:
десять 401, двенадцать 429 с `Retry-After` 59–58; через минуту снова 401). При
полном счётчике тот же запрос с `-H 'X-Forwarded-For: 198.51.100.77'` обязан
получить 429, а не 401: 401 значил бы, что клиент сам называет адрес и получает
новый счётчик на каждый запрос. 2026-10-12 — 429, как и с `X-Real-IP` и
`Forwarded`.

**В браузере получателя** адрес с токеном остаётся в истории: токен входа к
этому времени погашен, токен создания пароля жив, пока пароль не задан и не
вышли 30 минут. Так было и с прежними ссылками.

`GET /auth/verify?token=…` API по-прежнему принимает: им входят тесты, e2e и
нагрузочный скрипт. Письма так не ходят. Такой запрос Caddy запишет с токеном
(журнал API — без строки запроса, «Журнал API: строка запроса скрыта» выше);
ненулевой счёт при проверке выше может быть и от него.

Что лежит у пользователя (значение токена не выводится; время в базе — UTC):

```bash
sudo -u postgres psql -X pharmacy_monitor -c \
  "select id, role, is_active, password_hash is not null as has_password,
          length(magic_token) as stored_len, magic_token_expires_at, last_login_at
   from tenant_users order by id;"
```

| `stored_len` | Что это |
|---|---|
| 64 | Хеш токена. Действует, пока `magic_token_expires_at` впереди |
| 43 | Токен открытым текстом — его оставил код до 2026-10-10 (тот не стирал токен, по которому не вошли). Входом не служит: от присланного всегда берётся хеш. 2026-10-10 на проде такая строка одна, срок вышел 5 октября |
| пусто | Ссылку не выдавали либо она погашена. `has_password = f` при свежем `last_login_at` — ссылкой воспользовались, а пароля нет: либо по ней вошли через `/auth/verify`, не задавая пароль, либо это след кода до второй правки от 2026-10-10 (создание пароля сорвалось уже после гашения). В обоих случаях нужна новая ссылка. 2026-10-10 на проде таких строк нет |

Выложена ли правка — смотреть работающий процесс, а не файл: API читает код при
старте, а выкладка сначала копирует файлы и только потом, после сборки
фронтенда, перезапускает его.

```bash
grep -c _magic_token_hash /opt/pharmacy-monitor/src/tenants.py   # 0 — не выложено
stat -c %y /opt/pharmacy-monitor/src/tenants.py
systemctl show pharmacy-monitor-api -p ActiveEnterTimestamp       # должен быть позже файла
```

Пока API не перезапущен, он пишет токены открытым текстом: строка длиной 43 в
эти минуты — свежая, а не старая.

Вторая правка от 2026-10-10 (гашение одним запросом, пароль проверяется до
токена) выкладывается отдельно и проверяется так же — по процессу:

```bash
grep -c redeem_magic_token /opt/pharmacy-monitor/src/tenants.py   # 0 — не выложено
grep -c _usable_new_password /opt/pharmacy-monitor/src/api.py     # 0 — не выложено
```

Схему она не меняет, миграций нет. Текст отказа на странице создания пароля и в
настройках берёт фронтенд. Страница создания пароля, открытая до выкладки, на
длинный пароль покажет вместо текста «[object Object]» (прежний код страницы не
читает причину отказа) — ссылку это уже не сжигает, страницу достаточно
обновить.

Строки с длиной 43 можно стереть в любой момент после перезапуска API — только
по слову владельца, это запись в боевую базу:

```sql
update tenant_users set magic_token = null, magic_token_expires_at = null
where magic_token is not null and length(magic_token) <> 64;
```

**Откат кода на версию до 2026-10-10.** Она сравнивает колонку с присланным как
есть, и хеш, выданный новым кодом, для неё — токен: кто прочитал базу, вошёл бы
по хешу, пока не вышел срок. Поэтому выданные ссылки стирают тем же запросом без
условия по длине дважды: перед выкладкой старого кода и сразу после перезапуска
API — пока идёт сборка фронтенда, новый код ещё выдаёт ссылки.

### Фильтр в журнале Caddy (второй слой)

Что он делает. Caddy пишет о запросе в двух местах, и в образце
`infra/Caddyfile` фильтр стоит в обоих:

- блок `log` сайта — запись о каждом запросе;
- общий блок `log default` — туда Caddy пишет **вторую** запись о запросе,
  который не смог обслужить сам (сервис за ним не ответил или перезапускается:
  502), с тем же адресом и теми же заголовками. API перезапускается при каждой
  выкладке, так что такие записи бывают.

У параметра запроса с именем, похожим на секрет, значение заменяется на
`<hidden>` — в адресе запроса, в `Referer` и в `Location` редиректа; заголовки
`Next-Router-State-Tree` и `X-Api-Key` в запись не идут вовсе. Имена — те же,
что у слоя Sentry (`_CREDENTIAL_NAME_RE` в `src/observability.py`: `auth`,
`cookie`, `token`, `secret`, `session`, `passw`, `pwd`, `signature`, `api_key`
— в любом месте имени, без учёта регистра), и ещё `key` и `code`, но только
именем целиком. Остальные параметры читаются как раньше
(`?search=kreon&min_spread=5`). Cookie и Authorization Caddy закрывает сам, а
ключ API в заголовке `X-Api-Key` без фильтра пишет целиком.

Чем проверено. `tests/test_caddy_log_filter.py` поднимает настоящий Caddy на
образце целиком (подменены адрес сайта и порты, один сервис «лежит») и ищет
значения в том, что он записал; контрольный запуск без фильтра обязан их
записать — в том числе в записи об ошибке. Пройдено руками 2026-10-12 на Caddy
2.6.2 и 2.10.2. ⚠️ В CI Caddy нет — там идут только проверки по тексту образца:
блок, написанный с ошибкой в строении, CI пропустит, его ловит `caddy validate`
в порядке ниже. Версия Caddy на сервере из репозитория не видна, и живой
`/etc/caddy/Caddyfile` от образца отличается: первый шаг — посмотреть обе вещи.

Чего фильтр не делает:

- это список имён: секрет в параметре с другим именем (`otp`, `jwt`, `sig`) или
  в пути адреса пройдёт;
- имя, записанное кодами знаков (`%74oken=…`), он не узнаёт, а API такой
  параметр принимает. Так пишет только тот, кто делает это нарочно;
- параметр, в имени которого есть слово из списка, скрывается тоже: `author`
  содержит `auth`. Сегодня у API таких параметров нет; новый параметр с таким
  именем из журнала пропадёт молча;
- записи, сделанные до установки, остаются до ротации.

**Поставить (root, только по слову владельца; сайт недоступен на время
перезапуска Caddy — секунды).** Правится копия, живой файл заменяется уже
проверенным:

```bash
caddy version
systemctl show caddy -p User                          # от чьего имени идёт служба
grep -n -B2 -A10 '^\s*log\b' /etc/caddy/Caddyfile     # какие блоки log стоят сейчас
M=$(date +%Y%m%d-%H%M)
cp -a /etc/caddy/Caddyfile /etc/caddy/Caddyfile.bak.$M
cp -a /etc/caddy/Caddyfile /etc/caddy/Caddyfile.new
nano /etc/caddy/Caddyfile.new
```

Две правки, обе — текстом из `infra/Caddyfile` репозитория; остальной файл не
трогать и образец поверх не копировать:

1. В блоке `log` сайта строку `format console` заменить блоком
   `format filter { … }` — десять строк, от `format filter {` до его закрывающей
   скобки. Если у живого блока формат другой (`format json`) — поставить его в
   строке `wrap console`; если строки `format` нет — `wrap json`: так Caddy пишет
   под systemd, когда формат не задан.
2. В общий блок в начале файла (где `admin off`) добавить блок `log default { … }`
   целиком. Если общий `log` там уже есть — не добавлять второй, а вписать в
   него `format filter { … }` с тем форматом, что в нём стоит.

Проверять от имени службы (строка `User=` из первой команды, обычно `caddy` —
она и стоит в командах ниже), а не root: `validate` создаёт файлы, на которые
ссылается конфигурация, и файл журнала, созданный root, служба потом не откроет
(при записи в journald, как в образце, этого файла нет).

```bash
sudo -u caddy caddy validate --config /etc/caddy/Caddyfile.new --adapter caddyfile   # ждём «Valid configuration»
cp -a /etc/caddy/Caddyfile.new /etc/caddy/Caddyfile
systemctl restart caddy && systemctl is-active caddy          # reload при `admin off` не работает
```

`validate` отказал — не ставить: живой файл не тронут, удалить `Caddyfile.new`.
«unrecognized», «module not registered» — версия Caddy фильтра не знает,
сообщить её. Жалоба на пустое значение — в файле стоит `{$ИМЯ}` из окружения
службы, которого у `sudo` нет: посмотреть `systemctl show caddy -p Environment
-p EnvironmentFiles` и передать переменную в команду.

Проверить на живом сайте — запрос с меткой и его запись. Метка своя на каждую
попытку, иначе в счёт попадёт прежняя:

```bash
P=probe-$(date +%s)
curl -s -o /dev/null -w '%{http_code}\n' "https://leaddrive.cloud/health?token=$P-CANARY&search=$P-KEPT"   # 200
sleep 1
journalctl -u caddy --since '-2 min' -o cat | grep -c -- "$P-CANARY"    # ждём 0
journalctl -u caddy --since '-2 min' -o cat | grep -c -- "$P-KEPT"      # ждём 1
```

Это проверяет запись о запросе. Запись об ошибке (второй блок) на живом сайте
без остановки сервиса не вызвать — её проверяет тест; на сервере посмотреть,
что блок встал: `grep -c 'format filter' /etc/caddy/Caddyfile` даёт 2.

Откат — если сайт не отвечает 200, записи с меткой `KEPT` нет или счёт `CANARY`
не ноль:

```bash
cp -a /etc/caddy/Caddyfile.bak.$M /etc/caddy/Caddyfile
sudo -u caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile && systemctl restart caddy
```

На сервере этот порядок не исполнялся ни разу (2026-10-12): сколько длится
перезапуск и что напишет `caddy validate` тамошней версии, покажет первый раз.
Стоит ли фильтр — `grep -c 'format filter' /etc/caddy/Caddyfile` (0 — нет, 2 —
оба блока).

### Email — слишком много писем (volume controls)

**Симптом:** клиент жалуется, что писем приходит больше, чем ожидает (напр.
«поставил дайджест раз в неделю, а капает по несколько раз в день»).

**Контекст:** на `EMAIL_TO`/recipients идут НЕСКОЛЬКО независимых потоков, и
per-user тумблеры daily/weekly (`tenant_users`, страница «Пользователи»)
управляют ТОЛЬКО per-user дайджестом. Остальные — отдельные механизмы:

| Поток | Источник | Как выключить | Как включить обратно |
|---|---|---|---|
| Мгновенные undercut/price-change алерты | Верифицированный полный `run` → `evaluate_rules` → `dispatch_events_batch` | отключить правило или получателя в UI; расписание не должно добавлять `--no-alerts` | включить правило/получателя и применить `install_systemd_schedule.sh` |
| Priority watchlist price-change | `watchlist-tick` каждые 3ч по confirmed URL; только локальная цена того же SKU | `systemctl disable --now pharmacy-monitor-watchlist.timer` | добавить confirmed URL и включить timer |
| Полный отчёт скрейпа (HTML+Excel, тема «Pharmacy Monitor DD.MM.YYYY — N undercuts») | `run_cmd` в конце КАЖДОГО не-hourly прогона — nightly **и intraday-tick** (`hourly=False`, до ~13/день 05–17 UTC) | `SCRAPE_REPORT_EMAIL=0` в `/etc/pharmacy-monitor/env` (next scrape) | `SCRAPE_REPORT_EMAIL=1` или убрать строку |
| Daily-дайджест (тема «Дайджест за сегодня», топ-N за 24ч) | `digest@daily.timer` → `pharmacy-monitor digest` → `src/digest.py` | `systemctl disable --now pharmacy-monitor-digest@daily.timer` | `systemctl enable --now …` |
| Недельный per-user дайджест | `digest-weekly.timer` Пн 06:00 UTC → `notify digest weekly` → `src/notifications.py` (`tenant_users.weekly_digest`) | per-user тумблер в UI / `systemctl disable …` | UI / `systemctl enable …` |
| Утреннее письмо с разницей цен (с 2026-10-13; на сервере — после установки таймера) | `digest-daily.timer` 05:00 UTC → `notify digest daily --locale az` → `src/notifications.py` (`tenant_users.daily_digest`) | per-user тумблер в UI / `systemctl disable --now pharmacy-monitor-digest-daily.timer` | раздел «Утреннее письмо с разницей цен» |

**Важно — два разных тумблера, два разных отката:** отчёт-письмо гасится
**env-флагом**, daily-дайджест — **состоянием systemd-юнита**. При откате нужно

```bash
cat data/daily_letter_state.json    # запись для сторожа: время, сколько слали и приняли
```

Так сразу видно, принял ли письмо почтовый сервер, и сторож начинает работать с
этой минуты, а не с первого запуска таймера. Запускать из
`/opt/pharmacy-monitor`: путь к файлу состояния по умолчанию относительный, и
health читает его из этого каталога. И под `pm`, как юнит: файл в `logs/`,
созданный из-под root, `pm` потом не допишет. Файл состояния на случай такой
ошибки пишется с правами 0644 — запись, сделанную из-под root, health под `pm`
всё равно прочтёт.

Выключить письмо: снять галочку у получателей — без подписчиков сторож молчит,
а таймер пусть работает. Если выключать таймер
(`systemctl disable --now pharmacy-monitor-digest-daily.timer`), а подписчики
остаются, сторож через 26 часов сообщит, что письмо не рассылалось, и будет
напоминать раз в сутки: тогда же удалить `data/daily_letter_state.json`.
⚠️ У таймера `Persistent=true`: по документации systemd, включённый после
перерыва, он сразу запустит пропущенное письмо. Если это не нужно — перед
включением `systemctl clean --what=state pharmacy-monitor-digest-daily.timer`.
На сервере не проверялось.

**Коды выхода `notify digest daily`.** Сначала отправляется всё, что можно, и
пишется запись для сторожа; потом команда решает, чем кончиться.

| Код | Когда | Что напечатано |
|---|---|---|
| 0 | Письмо принято почтовым сервером у всех получателей, отчёт на месте (или его нет по известной причине) | `OK: daily digest: принято у N из N получателей` |
| 0 | Принято не у всех, но хотя бы у одного. Письмо ушло, поэтому не ошибка, — но и не «OK»: админу об этом скажет сторож | `daily digest: принято у K из N получателей — кому не ушло, см. digest_email_failed в журнале` |
| 0 | Слать было нечего или некому | `OK: daily digest sent to 0 recipients` |
| 1 | Отчёт о ценах не собрался — и когда письмо с событиями ушло без него, и когда слать стало нечего, и при `--dry-run` | `Error: отчёт о разнице цен не собрался (<класс ошибки>) …` |
| 1 | Письмо слали, но сервер не принял его ни у одного получателя (отказ, сеть, пустой `SMTP_HOST`) | `Error: почтовый сервер не принял письмо ни у одного из N получателей …` |
| 1 | `--only <адрес>`, а такого адреса среди включивших суточный дайджест нет | `Error: получателя с таким адресом среди включивших суточный дайджест нет — письмо не отправлено` |

Код 1 кладёт юнит таймера в `failed`; повторной отправки нет. Недельный дайджест
этим правилам не следует: его коды и строка итога не менялись (в том числе
`--only` с адресом, которого нет, у него по-прежнему «sent to 0 recipients», код 0).

**Сторож: health замечает утро без письма.** Юнит в `failed` никто не увидит,
поэтому исход каждой настоящей рассылки пишется в файл, а часовой
`health-check --alert-email` (`pharmacy-monitor-health.timer`) его сверяет и
шлёт админу то же письмо о проблемах, что и об остальном
(`health._check_daily_letter`, `src/daily_letter_state.py`).

- Файл — `data/daily_letter_state.json` в `/opt/pharmacy-monitor` (другой путь —
  `DAILY_LETTER_STATE_FILE` в env). В нём: когда закончилась рассылка (UTC),
  скольким письмо слали, у скольких его принял сервер, что с отчётом — `ok`,
  `skipped:<причина>` или `failed:<класс ошибки>`. Адресов нет.
- Пишет его настоящая рассылка: запуск таймера и ручной `notify digest daily`.
  Не пишут `--dry-run`, `--only` и кнопка «Отправить тестовый дайджест» в
  дашборде — это письмо одному, а не рассылка. Запуск, в котором слать было
  нечего или некому, тоже пишет — иначе тихое утро выглядело бы пропущенным.
  Права на файл — 0644: читать его должен health, кто бы ни запускал рассылку.
- Проверка идёт, только если у арендатора есть активные получатели с суточным
  дайджестом и запись уже есть. Нет записи — проверки нет: включение подписки
  не поднимает тревогу до первой рассылки (поэтому первое письмо и отправляют
  руками).

| Код проблемы | Уровень | Когда |
|---|---|---|
| `daily_letter_overdue` | critical | Последняя рассылка старше 26 часов: таймер не сработал, команда упала раньше рассылки или не смогла записать исход |
| `daily_letter_not_delivered` | critical | В последней рассылке письмо слали, но сервер не принял его ни у одного получателя |
| `daily_letter_partly_delivered` | warning | Сервер не принял письмо у части получателей: команда кончилась кодом 0, админ свою копию получил, а клиент мог не получить. Кому не ушло — `user_id` в событиях `digest_email_failed`; кто это — запрос из «Email не приходит» |
| `daily_letter_report_failed` | warning, если письмо кому-то ушло; critical, если никому | В последней рассылке не собрался отчёт о ценах |
| `daily_letter_report_skipped` | warning | Отчёта в последней рассылке не было по известной причине: сравнения приостановлены политикой (`full_catalog_trust_not_ready`, страница отвечает 503), успешного сбора ещё не было, сравнивать нечего. Команда при этом кончается кодом 0, а письмо уходит без чисел и файла — или не уходит вовсе, если нет и событий. Так будет каждое утро, пока причина не снята; health напоминает раз в сутки |
| `daily_letter_state_unreadable` | warning | Файл состояния есть, но не читается: сторож не работает |

Проблем бывает две сразу — одна про отчёт, другая про доставку (отчёта не было и
письмо принято не у всех). «Давно не рассылалось» — всегда одна: прошлый исход
уже не новость.

26 часов — письмо раз в сутки и запас на случайную задержку таймера, саму
рассылку и позднее утро после простоя сервера (`daily_letter_state.MAX_AGE_HOURS`;
тест сверяет порог с файлом таймера). Отсюда задержка: о письме, не ушедшем в
05:00 UTC, health скажет в 08:00 UTC (12:00 Баку).

После простоя сервера возможна одна ложная тревога «не рассылалось N ч»: у
таймеров письма и health `Persistent=true`, оба стартуют вместе, и health может
успеть раньше письма. Через час, после догнавшей рассылки, придёт `RECOVERED`.
По документации systemd; на сервере не наблюдалось.

Оба уровня доходят до письма админу: новая проблема — сразу, та же — напоминание
раз в сутки. После удавшейся рассылки проблема из отчёта health уходит; если
других проблем нет, приходит `Pharmacy Monitor — RECOVERED` (как у остальных
проблем health, «Проверить здоровье системы»). Сторож судит по ПОСЛЕДНЕЙ
рассылке: неудачный ручной запуск в полдень перекроет удачное утро, и наоборот
(кнопка в дашборде запись не трогает).

Заглушить проблему сторожа нельзя — только снять причину. Адрес, который
почтовый сервер отвергает каждое утро, даёт предупреждение
`daily_letter_partly_delivered` с напоминанием раз в сутки, и пока оно висит,
вместо `RECOVERED` по другим проблемам приходит письмо `WARNING`. Что делать:
исправить адрес или снять у этого `user_id` галочку суточного дайджеста —
проблема уйдёт после следующей рассылки в 05:00 UTC. Убрать её сразу можно,
только удалив `data/daily_letter_state.json`: сторож после этого слеп до
следующей настоящей рассылки.

```bash
# что записано о последней рассылке и что об этом думает health
cat /opt/pharmacy-monitor/data/daily_letter_state.json
journalctl -u pharmacy-monitor-health --since today --no-pager | grep daily_letter
```

**Ушло ли и почему нет.**

```bash
journalctl -u pharmacy-monitor-digest-daily --since today --no-pager
systemctl status pharmacy-monitor-digest-daily.service --no-pager | head -5
```

| В журнале | Что значит |
|---|---|
| `digest_no_recipients kind=daily` | Суточный дайджест не включён ни у одной активной записи. Отчёт не собирался |
| `digest_price_report compared=… differing=… attachment_kb=… overdue_sites=[…]` | Отчёт собран; эти числа — в письме |
| `digest_price_report_skipped reason=…` | Отчёта нет: `no_successful_run`, `full_catalog_trust_not_ready` (политика), `no_comparison_rows` |
| `digest_price_report_failed error_type=…` и трассировка | Сборка отчёта упала. Были события — письмо ушло без отчёта; не было — не ушло ничего. В обоих случаях `Error: отчёт о разнице цен не собрался (…)`, код 1, юнит в `failed`, сторож сообщит админу |
| `digest_no_events kind=daily` | Ни отчёта, ни событий — письма нет |
| `smtp_send recipients=1`, следом `smtp_sent_ok` | Почтовый сервер принял письмо этому получателю. Дошло ли — кабинет Resend |
| `digest_email_failed user_id=… error_type=…` | Этому получателю не ушло; разбор — «Email не приходит». Не ушло никому — код 1 |
| `digest_sent kind=daily recipients=N events=M` | Итог. `recipients` считает и письма, которые не ушли из-за пустого `SMTP_HOST` (`email_skipped_no_smtp`): верить `smtp_sent_ok` и коду выхода |
| `daily_letter_state_write_failed path=… error_type=…` | Запись для сторожа не удалась (права, диск). Письмо при этом ушло и код 0, но через 26 часов сторож скажет «не рассылалось» |

Юнит в `failed`: одна из строк `Error:` (отчёт не собрался, сервер не принял
письмо ни у кого — «Коды выхода»), команда не уложилась в `TimeoutStartSec`
(15 минут) или упала раньше письма — тогда в журнале трассировка (недоступна
база, не читается env).

**Чего письмо НЕ делает.**

- Не говорит, что изменилось со вчера: числа — состояние на утро. Полный сбор
  сайтов недельный (`src/cadence.py`) — на момент записи; ежедневный сбор идёт
  отдельным PR. Пока ритм недельный, между сборами цены pharmonline и
  aptekonline не обновляются, aloe — частями; в такие дни письмо почти
  повторяет вчерашнее.
- После неудачной ночи не ждёт проверенных цен. Пока последняя полная попытка
  хотя бы одного сайта неудачна, страница сравнения (в режиме политики `shadow`)
  читает последние записанные цены вместо проверенных — и письмо, собранное тем
  же кодом, тоже: числа и файл считаются и по тому, что успел записать упавший
  сбор. В письме об этом одна жёлтая строка «Данные <сайт> — от …».
- Не проверяет доставку: `smtp_sent_ok` значит только, что сервер письмо принял.
  Письмо, принятое сервером и не дошедшее (спам, отказ после приёма), не видят
  ни команда, ни сторож — только кабинет Resend.
- Не кончается ошибкой, когда письмо не принято у части получателей: одному
  ушло — код 0. Строка итога при этом честная («принято у K из N»), а админу о
  непринятых пишет сторож (`daily_letter_partly_delivered`).
- Не повторяет отправку: что не ушло утром, само не уйдёт.
- Сторож не работает, пока не было первой настоящей рассылки, и узнаёт о
  пропущенном утре через 2–3 часа, а не сразу.
- Сторож шлёт своё письмо той же почтой. Если почтовый сервер не принимает
  ничего, не дойдёт и тревога о письме: останутся юнит в `failed`, код выхода
  `health-check` и `/status` в Telegram (бот не настроен).
- Сторож не знает, кому именно не ушло (только сколько; кому — в журнале по
  `user_id`) и сколько получателей должно быть: он сравнивает числа одной
  рассылки. Снятую по ошибке галочку у клиента он не заметит.
- Разбивка «у кого дешевле» считается для сайта клиента из записи арендатора
  (`tenants.client_site`), а колонка «Позиция» в файле написана про
  Pharmonline: у арендатора с другим сайтом клиента они разойдутся. Арендатор
  сейчас один.

Не проверено на 2026-10-13: отправка настоящим почтовым сервером и примет ли он
вложение; юнит под systemd на сервере; что `pm` из юнитов письма и health на
сервере действительно пишет и читает один и тот же
`data/daily_letter_state.json` — по файлам юнитов в репозитории это так (один
пользователь, один рабочий каталог, запись в `data/`; на это есть тест), а
юниты на сервере могут отличаться. Письмо сторожа на живой системе не
приходило ни разу. Проверено: на свежей копии боевой базы (не на сервере) письмо
собирается за 2,9 с, вложение — 773 КБ, числа сходятся (замер 2026-10-13);
тесты на SQLite (`tests/test_daily_price_letter.py`,
`tests/test_daily_letter_watchdog.py`, `tests/test_digest_daily_unit.py`); два
теста на PostgreSQL написаны, но исполняются только в CI.

### Firecrawl fallback для Pharmonline

Decodo остаётся основным источником. Автоматический workflow переходит на
Firecrawl **только** после трёх неуспешных свежих попыток Decodo и лишь при
явном включении в `/etc/pharmacy-monitor/env`:

```bash
FIRECRAWL_API_KEY=fc-...  # секрет, не коммитить
PHARMONLINE_PUBLIC_API_FIRECRAWL_FALLBACK=required
PHARMONLINE_FIRECRAWL_MAX_REQUESTS=140
```

Fallback читает `rawHtml` API/ sitemap c `maxAge=0`, `storeInCache=false` и
`proxy=basic`. Каждый ответ обязан быть HTTP 200, basic и ровно 1 credit;
изменение тарифа, cache/advanced-proxy или неполный sitemap отклоняют весь
прогон без обновления каталога. На текущем каталоге ожидается до 131 запроса
за полный проход; лимит 140 — предохранитель, а не цель для расхода.

```bash
# Текущее состояние всех email-потоков
ssh root@13.140.186.143 '
  grep "^SCRAPE_REPORT_EMAIL=" /etc/pharmacy-monitor/env || echo "(report email: ON — флаг не задан)"
  systemctl is-enabled pharmacy-monitor-digest@daily.timer pharmacy-monitor-digest-weekly.timer
  systemctl is-enabled pharmacy-monitor-digest-daily.timer   # утреннее письмо; "not-found" — таймер не ставили
  systemctl list-timers --all | grep -i digest
'
# NB: есть templated-юнит pharmacy-monitor-digest@weekly.timer (слал бы 24ч-дайджест
# на EMAIL_TO еженедельно) — он должен быть DISABLED, иначе лишний недельный блок.
```

### Сбор pharmonline: новые товары допускаются сами, остальное — ручная сверка

Полный сбор pharmonline (`run --site pharmonline`, режим `public_api`) пишет
каталог, только если у каждой пары «идентификатор + адрес» есть доверенное
происхождение: история DDP, запись ручной сверки или допуск. До 2026-10-08 допуск
писала одна ручная сверка, новые товары появляются на сайте почти каждый день, и
сбор жил от сверки до первого нового товара (после сверки 2026-10-04 — 14 часов).

**Что сбор теперь допускает сам** — два класса, оба без свидетельства со стороны
сайта:

- новый товар — ни идентификатора, ни адреса нет ни у одного тенанта;
- вернувшийся товар — строка с тем же идентификатором и тем же адресом уже
  лежит в базе без DDP-истории (товар сняли с сайта до июля 2026, когда
  появилась история наблюдений; таких строк на 2026-10-08 около 260, и новых
  не прибавляется).

Условия, все сразу: план сверки безопасен целиком; в нём нет ни перекодировки,
ни смены адреса, ни разведения; допусков не больше 150 за прогон; после допуска
в той же транзакции каталог проходит полную проверку личностей. Не выполнено
любое — не допускается ничего, сбор отказывает как раньше.

(⚠️ С правки 2026-10-13, ежедневный сбор: понедельничного запуска из GitHub
Actions по расписанию больше нет — тот workflow остался ручным. «Еженедельный
сбор из Actions» в этом разделе читать как его ручной запуск; pharmonline каждую
ночь собирает таймер сервера.)

Так ведёт себя любой полный сбор pharmonline в режиме `public_api`: ночной
таймер, еженедельный сбор из GitHub Actions, `--force`, кнопка в дашборде, шаг
сбора в workflow ручной сверки. `--dry-run` тоже допускает (он и сбор пишет
по-настоящему) и письмо админу тоже шлёт: флаг придерживает только то, что
читает клиент, — алерты и отчёт. Транспорт — `direct`, `decodo` или `firecrawl`;
с `crawlbase` и `scraperapi` сбор сам не допускает (транспорты в коде остались, а ручные
workflow, которые ими ходили, удалены 7–8 октября 2026).

⚠️ Уточнение 2026-10-14 (разбор `main` на `0fdcc366`, сверено по коду и серверу):
кнопка в дашборде в этот список попала по ошибке — её сбор pharmonline идёт без
допуска и без проверки личностей. Вотчер очереди
(`infra/server/watch-scrape-queue.sh`, на сервере та же строка) зовёт
`run --mode category --no-alerts --request-id N`. Маркер, переводящий сбор
pharmonline в `public_api`, срабатывает только в режиме `auto` и только когда
сайт один (`_pharmonline_public_api_autonomous_mode_requested`), допуск
вызывается только при `use_public_api`, а в `/etc/pharmacy-monitor/env` строки
`PHARMONLINE_PUBLIC_API=` нет, зато есть `PHARMONLINE_USE_DDP=1` (сверено
2026-10-14 подсчётом строк). Значит, запрос кнопки, в который входит pharmonline
(в том числе без выбора сайтов — тогда собираются все три), собирает его путём
категорий, а сборщик для него по этому env — DDP (`_pharmonline_scraper_class`).
По коду (прогоном не проверено) из этого следует:

- такой сбор пишет каталог по категориям по ходу сбора, без проверки личностей
  и без допуска — без строки в журнале допусков, без потолка 150 и без письма
  админу; а наблюдения с источником `pharmonline_ddp_total_count` проверка
  личностей потом считает доверенной историей. То, что кнопка запишет через
  DDP, следующие ночные сборы примут без допуска;
- без категории и лимита это полная попытка (`catalog_scope = 'full'`) для
  каждого сайта запроса, а доверие к каталогу сайта решает последняя полная
  попытка (`product_policy._site_full_run_state`). Не удастся она — проверенных
  цен и рекомендаций нет до следующего удачного сбора, а при нажатии без выбора
  сайтов — у всех трёх.

**Потолок и рубильник.** `PHARMONLINE_PUBLIC_API_SCHEDULED_ADMISSION_LIMIT` в
`/etc/pharmacy-monitor/env`: число меньше 150 снижает потолок, `0` выключает
автодопуск (сбор снова отказывает на первом новом товаре), больше 150 и
нечитаемое значение потолок не поднимают (нечитаемое — выключает). Еженедельный
сбор из GitHub Actions читает тот же файл.

**В письме товар, которого быть не должно.** Чистить ничего не надо. Допуск
утверждает только «сайт назвал этот идентификатор по этому адресу, и в базе ему
ничто не противоречило» — это остаётся правдой. Дальше это обычный товар
каталога: пропадёт с сайта — перестанет обновляться, как любой снятый; сайт
переселит его на другой адрес — сбор остановится до ручной сверки. Журнал
допусков только дописывается, строки из него и из `products` не удалять (на них
ссылаются цены и наблюдения). Если лишних товаров много и это повторяется —
остановить автодопуск (`…_LIMIT=0`) и разбираться с сайтом.

**Сбор упал уже после допуска.** Допуск фиксируется до записи сбора, поэтому
остаются товар без цены и его допуск — то же состояние, что между ручной сверкой
и следующим сбором. Ничего чистить не надо: следующий сбор считает товар
доверенным и запишет цену. В упавшем прогоне допуск виден
(`run_quality.pharmonline_identity_admission`). Что при этом видит клиент: в
списке товаров дашборда (он отсортирован по времени последнего наблюдения) такие
товары стоят первыми с пустой ценой, пока не пройдёт следующий сбор, — у ночного
таймера это следующая ночь. Так выглядел прод 2026-10-08 после ручной сверки,
за которой не прошёл сбор (15 товаров без цены).

### Поиск на странице сравнения не находит товар / находит не сразу

Поиск, подсказки и выгрузка в Excel на `/comparison` работают через индекс
названий в памяти процесса API (`src/catalog_search.py`), а не через SQL.

- **У каждого воркера свой индекс.** Он собирается при старте воркера в фоне
  (в журнале `catalog_search_index_built products=… seconds=…`) и обновляется
  тоже в фоне: когда завершился прогон или появились новые товары, но не чаще
  раза в минуту, и в любом случае раз в 30 минут. Запрос обновление не ждёт —
  до его конца отдаётся прежний индекс.
- **Товар только что появился в базе, а поиск его не видит** — это нормально в
  пределах минуты. Дольше 30 минут — смотреть журнал на
  `catalog_search_index_refresh_failed`. Сбросить индекс принудительно можно
  только рестартом `pharmacy-monitor-api`: `catalog_search.reset_cache()`
  действует на тот процесс, где вызван, скрипт обслуживания воркеры не сбросит.
- **В индексе только названия и бренды.** Цены, пары и наличие читаются из базы
  на каждый запрос, поэтому устаревший индекс не может показать неверную цену
  или чужого арендатора — только не найти новый товар.
- **Товар найден, но в блоке «найдено на сайтах, но не в сравнении»** — у него
  нет пары на другом сайте (или пара скрыта фильтром «на N сайтах»). Это вопрос
  сопоставления, а не сбора: связать вручную можно на странице «Подбор матчей».
- **Память:** около 50 МБ на воркер при 45 тыс. товаров, вдвое больше на время
  пересборки.

### На странице сравнения мало строк / пришло мало алертов «конкурент дешевле»

Денежные выводы (сравнение в режиме доверенной эпохи, рекомендации, алерты)
читают цену только из `price_snapshots`, и только из записей, которым доверяют.
Другого источника цены нет: `offer_observations` хранит страну и наличие, но не
цену. Товар без доверенной записи из этих выводов выпадает, даже если цена у
него есть.

Записи доверяют в двух случаях (`storage.trusted_snapshot_filter`):

- её сделал проверенный полный сбор (`run_id`);
- проверенный полный сбор позже увидел товар с той же ценой и пометил запись
  (`confirmed_run_id`). `price_snapshots` — журнал изменений, при прежней цене
  новая строка не пишется, поэтому без пометки цена, которую первым записал
  прогон без проверки, не становилась доверенной никогда.

Пометки ставит шаг пайплайна после проверки каталога, до алертов
(`prices_confirmed_by_verified_runs` в журнале сбора, со счётчиком по каждому
прогону). Он проходит по текущему сбору, по последнему проверенному сбору
каждого сайта и по предыдущему проверенному сбору своего; повтор ничего не
меняет. Сбор, не прошедший проверку, ничего не подтверждает.

Сколько товаров сейчас без доверенной цены:

```sql
with elig as (
  select id from runs
  where status = 'ok' and finished_at is not null and catalog_scope = 'full'
    and catalog_verified and run_quality->>'financially_eligible' = 'true'
)
select p.site,
       count(*) as fresh,
       count(*) filter (where not exists (
         select 1 from price_snapshots ps
         where ps.product_id = p.id
           and (ps.run_id in (select id from elig)
                or ps.confirmed_run_id in (select id from elig))
       )) as no_trusted_price
from products p
where p.last_seen_at >= now() at time zone 'utc' - interval '8 days'
group by 1 order by 1;
```

- **`no_trusted_price` — тысячи.** Так было до 2026-10-07 (85% каталога). После
  выкладки подтверждения счётчик падает до десятков на первом же проверенном
  полном сборе любого сайта. Не упал — в журнале сбора нет строки
  `prices_confirmed_by_verified_runs`, то есть сбор не прошёл проверку:
  смотреть `runs` с `catalog_scope='full'`, колонки `catalog_verified` и
  `catalog_verification_reason`.
- **Десятки.** Товары, которые после последнего проверенного сбора своего сайта
  увидел только частичный тик или сбор, не прошедший проверку. Уйдут со
  следующим проверенным сбором.
- **Строк сравнения всё равно меньше, чем без эпохи.** Товар, которого нет в
  последнем проверенном сборе (снят с сайта), в режиме эпохи не показывается;
  без эпохи он виден с пометкой «N дн. назад». Замер 2026-10-07: 275 строк из
  3 789.
- **Письма «цена упала» нет, хотя цена упала.** Изменение первым записал прогон
  без права на алерты — intraday-тик или сбор, не прошедший проверку. Проверенный
  сбор подтверждает такую цену молча: для него она уже «прежняя».
- **В алерте «конкурент дешевле» цена конкурента старая.** Алерт считается в
  сборе одного сайта, а цену другого берёт на момент его последнего проверенного
  сбора. Если тот сайт давно не проходит проверку, цена будет соответствующего
  возраста: проверки свежести чужого сайта у алертов нет.

### Параметры упавшего запроса

**Симптом.** В ошибке запроса к базе — в журнале, в Sentry, в `runs.error_message` —
вместо параметров стоит `[SQL parameters hidden due to hide_parameters=True]`, а
после первой строки ошибки PostgreSQL —
`[details hidden: the full text is in the PostgreSQL log]`. У ошибок данных
(значение не подошло типу или не влезло в колонку) нет и первой строки:
`data exception, SQLSTATE 22001 [details hidden: ...]`.

Так задумано (правка 2026-10-11). Текст ошибки запроса расходится далеко: Sentry —
сторонний сервис, журнал шага GitHub Actions публичный, `runs.error_message`
показывает дашборд. Раньше в нём стояли данные запроса: параметры (токен входа,
адрес, хеш пароля), а при нарушении ограничения — вся строка таблицы, её приводит
сам PostgreSQL. Теперь от ошибки остаются класс (`UniqueViolation`,
`StringDataRightTruncation`), первая строка сервера и запрос с именами параметров
(`[SQL: ...]`). Устроено это в `src/storage.py`, рядом с
`create_engine_hiding_statement_data`.

**Полный текст ошибки сервера** — DETAIL, HINT, CONTEXT — лежит в журнале
PostgreSQL на сервере базы. Читают его `postgres`, root и группа `adm`; у `pm`,
под которым работает приложение и ходит CI, доступа нет — смотрит владелец под
root. Ротация раз в неделю, хранится десять архивов
(`/etc/logrotate.d/postgresql-common`):

```bash
# время взять из журнала приложения; у каждой ошибки рядом STATEMENT — сам запрос
zgrep -h -A4 "ERROR:" /var/log/postgresql/postgresql-16-main.log* | less
```

Подсказка сервера тоже только там. Сбор aloe, упавший на предохранителе, в своей
ошибке несёт «already stored under its site number», а строку
`HINT: Code older than migration ...` — уже нет.

**Параметры запроса** сервер по умолчанию не пишет
(`log_parameter_max_length_on_error = 0`; на проде так, проверено 2026-10-11).
Нужны для разбора — включить на время и повторить сбой:

```bash
sudo -u postgres psql -X -c "ALTER SYSTEM SET log_parameter_max_length_on_error = 200" \
                         -c "SELECT pg_reload_conf()"
# ... повторить сбой, прочитать журнал: строка CONTEXT ... with parameters: $1 = '...'
# (у ошибки типа — CONTEXT ... parameter $1 = '...': только тот параметр, что не подошёл)
sudo -u postgres psql -X -c "ALTER SYSTEM RESET log_parameter_max_length_on_error" \
                         -c "SELECT pg_reload_conf()"
```

⚠️ Пока настройка включена, в журнал PostgreSQL ложатся параметры упавших
запросов, в том числе токен входа и хеш пароля, — выключить сразу после разбора.
Замерено на PostgreSQL 16: параметры есть у нарушения ограничения, ошибки типа и
`statement_timeout`; у ожидания замка на таблице строки CONTEXT не было вовсе.
Те же параметры сервер в это время приписывает и к ошибке, которую отдаёт
приложению. В текст ошибки приложения они не попадают: всё после первой строки
отбрасывается, это проверяет `test_parameters_logged_by_the_server_are_not_printed`.
Запись в настройки сервера — действие на проде, его делает владелец.

Не трогая прод: повторить сбой на копии базы (рецепт одноразового PostgreSQL —
«Модели и миграции» ниже), там параметры можно писать без оглядки.

У теста, упавшего в CI, полный текст ошибки сервера есть в самом прогоне: в конце
журнала джобы `Test (pytest)` GitHub печатает журнал PostgreSQL целиком (блок
`Print service container logs`), с DETAIL и STATEMENT. Журнал этот публичный —
в тестовой базе держать только выдуманные данные.

**Выложена ли защита.**

```bash
grep -c create_engine_hiding_statement_data /opt/pharmacy-monitor/src/storage.py
```

Ноль значит, что на сервере прежний код и ошибки запросов печатаются с
параметрами (прочитано 2026-10-11: не ноль).

Тот же grep по `/opt/pharmacy-monitor/migrations/env.py` даёт ноль — **и должен
давать**: `env.py` живого каталога выкладка не трогает, там файл от 2026-08-23.
Руками его туда не копировать — почему, сказано в разделе о выкладке, «Откат
выкладкой прошлого коммита».

Миграция из `deploy.yml` от живого `env.py` не зависит. Workflow кладёт релиз в
`/opt/pharmacy-monitor/.deploy-stage.*` и исполняет `alembic upgrade` оттуда — на
`env.py` и `src` одного коммита, то есть через фабрику. Журнал шага публичный;
упавшая миграция данных печатает в него класс ошибки, первую строку сервера и
запрос с именами параметров — без значений и без строки таблицы. Проверено
настоящими сбоями на PostgreSQL 16 — ожидание замка строки, нарушение
уникальности и NULL в обязательной колонке (на нём сервер приводит всю строку
таблицы), с контролем на `env.py` с сервера: с ним те же сбои печатают адрес и
хеш (`tests/test_migration_lock_timeout.py`). Слово `LockNotAvailable`, по
которому `deploy.yml` повторяет попытку, в тексте остаётся. Действует это с
первой выкладки коммитом, в котором этот порядок есть: смотреть в журнале
прогона шаг «Stage release runtime».

⚠️ Всё, что исполняет Alembic из живого каталога, идёт на прежнем `env.py` и
данные упавшего запроса печатает. Таких путей два. `alembic`, запущенный на
сервере руками, печатает в терминал того, кто запустил, — как запускать,
сказано в разделе о выкладке, «Ручной alembic на сервере». И выкладка ветки, в
которой порядка из PR #35 нет: её исполняет прежний `deploy.yml` этой ветки, он
зовёт `alembic upgrade` из живого каталога, и упавшая миграция данных
напечатает параметры и строку таблицы в публичный журнал шага. Защита
принадлежит выкладываемому коммиту, а не серверу: ветку с миграцией перед
выкладкой догнать до `main`.

**Если в журнале или в Sentry снова появилось `[parameters:` или `DETAIL:`** —
где-то создан движок мимо фабрики (`tests/test_statement_data_stays_out_of_errors.py`
ловит это в `src/`, `migrations/` и в новых workflow, но не в `scripts/`) либо
ошибку печатает код, который сам достаёт данные из исключения (`exc.params`,
`exc.orig.diag`). Значение в первой строке ошибки (`no operand in tsquery: "..."`,
текст `RAISE EXCEPTION`) — не поломка защиты: первую строку вне ошибок данных она
оставляет как есть. Как убрать из публичного журнала уже попавшее — «Email не
приходит» выше, про удаление журнала прогона.

### В строке сравнения цены конкурентов есть, а цены клиента нет

**Симптом.** Клиент ищет товар, который у него точно продаётся; в строке
сравнения цены других сайтов, а его цены нет — или его цена стоит в соседней
строке с тем же названием. Так было с «Kreon 25000» (жалоба 2026-10-09).

**Сначала отличить от «не собрали».** Если строк товара в каталоге нет вовсе,
это сбор, а не сопоставление:

```bash
# на сервере, под root; в кавычках — слово из названия
sudo -u postgres psql -X pharmacy_monitor -v q="'%kreon%'" <<'SQL'
select p.id, p.site, left(p.name, 45) as name, p.canonical_id as cluster,
       to_char(p.last_seen_at, 'YYYY-MM-DD') as seen,
       (select coalesce(s.discount_price, s.price) from price_snapshots s
         where s.product_id = p.id order by s.captured_at desc limit 1) as price
  from products p where p.name ilike :q order by p.name_normalized, p.site;
SQL
```

Запрос идёт через stdin: в `-c` psql переменную `:q` не подставляет.

Один товар лежит двумя кусками, когда у одного сайта две строки с одним
названием в РАЗНЫХ кластерах и одну из них давно не видели (`seen` старше двух
недель): сайт сменил адрес товара, старая строка осталась в паре с товаром
клиента, новая сошлась с третьим сайтом отдельно.

**Что делает этап сопоставления.** Шаг `relink_stale_members` такие два кластера
сливает (с 2026-10-12). В журнале этапа — `matcher_split_clusters_merged`: для
каждого слияния оставшийся кластер (`match_id`), удалённый (`merged`),
пропавшая строка (`old`), перешедшие товары (`moved`) и отвязанные вместе с
ней пропавшие строки (`dropped`). Сколько таких случаев и что с ними будет, не
меняя базу:

```bash
# на сервере, под pm, с загруженным env; печатает список и выходит
cd /opt/pharmacy-monitor && sudo -u pm bash -c 'set -a; . /etc/pharmacy-monitor/env; set +a;
  .venv/bin/python -B -c "
from src import matcher, storage
with storage.make_session()() as s:
    for item in matcher.relink_stale_members(s, dry_run=True):
        print(item)
    s.rollback()"'
```

Вместе со списком команда печатает причины отказов — события
`matcher_split_merge_refused` с полем `reason`. В журнале юнита их нет: там
уровень INFO, а событие уровня debug. Команда берёт транзакционный замок
сопоставления: пока идёт сбор или `rematch`, она будет ждать — запускать, когда
прогона в работе нет. Проверена на копии базы 2026-10-12; на сервере работает
после выкладки правки (до неё шаг слияний не знает).

**Когда не сливает** — намеренно. Причины (`reason`) и что за ними стоит:

- `two_rows_of_one_site` — после слияния у сайта оказалось бы две ЖИВЫЕ строки:
  два предложения сайта, каждое уже в своём кластере. В 11 случаях из 28 на
  копии каталога у них и названия разные («Relif» и «Relif Advans»);
- `twin_is_another_product` — новая строка сайта не тот же товар, что старая:
  страна старой известна, а у новой другая или не подтверждена (правило клиента
  «разная страна — разный товар»);
- `members_must_not_meet` — товары двух кластеров нельзя сводить: отказ
  оператора либо конфликт, который не пропустил бы и обычный проход (страна,
  фасовка, доза);
- `live_row_without_pair_too` — у сайта есть ещё одна живая строка с этим
  названием, без пары: какая из двух продолжение пропавшей, не решить;
- `price_per_unit_mismatch` — цена за упаковку против цены за штуку;
- `member_not_matchable` — один из товаров не в наличии;
- `manual_cluster` — кластер двойника собран оператором (свой ручной кластер
  шаг пропускает молча, события нет);
- `nothing_to_bring` — в кластере осталась одна пропавшая строка, на экране
  этого не видно;
- `several_twins`, `site_twice_in_a_cluster`, `two_lost_rows_of_one_site` —
  выбрать нечем: двойников несколько, в кластере уже две строки сайта, обе
  строки сайта давно не видели.

Строку сайта, недавно собранного меньше чем наполовину, шаг пропавшей не
считает вовсе: «давно не видели» там значит «сбор не проходил». Условия
закреплены тестами — `tests/test_matcher_coverage.py`, раздел «Двойник уже с
парой».

**Готового пути у оператора для таких случаев нет.** Кнопка «Неправильное
сравнение?» товар, который уже состоит в другом сравнении, не принимает: ответ
409 «Этот товар уже в другом сравнении — сначала отклоните его там». Отклонить
— значит оставить постоянный отказ между товарами того сравнения; делать это
стоит, только если оно и правда неверное. У pharmonline старая и новая строки
товара нередко делят один адрес — тогда вставленный адрес находит старую, и
ответ 400 «Не удалось переназначить» (так вышло с «Linkas 120 ml»). Проверено
на копии базы 2026-10-12.

**Пропавшие строки новых пар не начинают** (с той же правки). Строка без пары,
которую давно не видели на собранном сайте, в проходах не участвует — в
журнале `matcher_gone_rows_skipped` с их числом (1 522 на копии каталога
2026-10-12). Без этого строки, освобождённые слиянием, сходились между собой:
второй кластер того же товара с устаревшими ценами. Кластеры из одних
пропавших строк, собранные раньше, остаются как были (27 на той же копии).

У правила две узкие цены (замер разбора 2026-10-12, на построенных примерах):

- строка, которая на сайте есть, но сбору не попадалась дольше двух недель
  (сайт при этом собран больше чем наполовину — частичными тиками), новой пары
  не получит, пока сбор её снова не увидит. `last_seen_at` сбор пишет до этапа
  сопоставления, так что товар, вернувшийся на сайт, сводится в том же прогоне;
- для сайта, которого нет в `src/cadence.py`, ритм считается суточным, и строка
  становится «пропавшей» через 54 часа после того, как её видели в последний
  раз (если больше половины каталога сайта за это время видели; сайт, который
  не собирали вовсе, пропавших строк не даёт). Новый сайт вносить в
  `cadence.py` до первого сопоставления.

Неоднозначность (`matcher_ambiguous_generics_suppressed`) пропавшие строки
по-прежнему создают: товар, подходящий к двум давно не виденным строкам сайта,
остаётся без пары, как и до правки. На копии так без пары один товар клиента
(«Roybos-miks+vitamin C №10»).

**После выкладки правки** этап запускают руками — команда `rematch` в разделе
«Выкладка правок сопоставления»; плановый юнит на сервере на 2026-10-12 прежний
и не отрабатывает. Вывод команды сохранять в файл (добавить в конец
`2>&1 | tee /root/pm-rematch-$(date +%F-%H%M).log`): при ручном запуске строка
`matcher_split_clusters_merged` идёт в терминал, а не в журнал сервера, и
другого следа у слияния нет.

**Откат слияний.** Слияние удаляет запись одной из двух пар, поэтому одного
снимка назначений товаров (`/tmp/pm-matching-before.csv`) для отката мало:
возврат товара в удалённую пару упирается во внешний ключ
(`products_canonical_id_fkey` — проверено на копии базы 2026-10-12). Нужен ещё
снимок самих пар, `/tmp/pm-matches-before.csv`. Его снимают один раз на
выкладку, до запуска этапа, — по чек-листу «Перед выкладкой» в «Выкладке правок
сопоставления», вместе с назначениями, — и уносят с сервера. **Здесь его не
переснимать** (до 2026-10-13 в этом месте стояла та же команда): выполненная
после этапа, она запишет в тот же файл пары «после» и затрёт снимок «до». Если
снимка, снятого до этапа, нет, по снимкам удалённые пары не вернуть: остаётся
бэкап, сделанный до этапа, а это уже восстановление, не откат, — остановиться
и показать владельцу. Бэкап перед этапом — в том же чек-листе.

Шаг 2 отката из «Выкладки правок сопоставления» выполняется так (`:m` —
сохранённый `max(id)` из `matches`; отличие от прежнего блока, оставленного
там для сравнения, — три строки с `matches_before`). Имена файлов в командах —
как в чек-листе; если снимки перед этой выкладкой сохранены под другими
именами, подставить их: откат по файлам от другой выкладки вернёт не то
состояние. Перед откатом посмотреть время записи —
`ls -l --time-style=long-iso /tmp/pm-match*before*`: нужные файлы записаны до
запуска этапа этой выкладки и после этапа предыдущей. Время в выводе — по
часам сервера (Europe/Berlin), а время мержа и выкладки в GitHub — UTC:
напрямую их не сравнивать. Так было 2026-10-13:
судя по времени записи, под именами из чек-листа на сервере лежали снимки от
2026-10-12 (перед этапом PR #95), а снятые перед этапом PR #97 — с датой в
имени (`/tmp/pm-matching-before-2026-10-13.csv`,
`/tmp/pm-matches-before-2026-10-13.csv`):

```sql
create temp table before (id int primary key, canonical_id int, name_normalized text, dosage text, pack_size text);
\copy before from '/tmp/pm-matching-before.csv' csv
create temp table matches_before (like matches);
\copy matches_before from '/tmp/pm-matches-before.csv' csv
begin;
insert into matches select * from matches_before b where not exists (select 1 from matches m where m.id = b.id);
update products p set canonical_id = b.canonical_id, name_normalized = b.name_normalized,
       dosage = b.dosage, pack_size = b.pack_size
  from before b where p.id = b.id;
update products set canonical_id = null where canonical_id > :m;
delete from matches where id > :m;
commit;
```

На копии базы после этапа с 16 слияниями это вернуло назначения всех товаров
и число пар к исходным. Поля самих пар (название, флаги), которые этап успел
поменять у уцелевших записей, откат не возвращает — как и прежний.

### В сравнении цена не та, что на сайте: в паре стоит другой товар

**Симптом.** Клиент открывает свой товар на сайте — цена одна; в сравнении или
в алерте «конкурент дешевле» у того же названия — другая. Жалоба 2026-10-12:
четыре алерта из одной рассылки. Цены в базе были свежие и верные; в парах
стояли разные товары с одним названием — таблетки и свечи («Polioksidonium
12 mq № 10» у клиента дважды: 19,20 и 27,60), крем и мазь («Ametazon 30 q»),
обычный «Septolete total» и лимонный, «Ringer» и «Ringer laktat».

**Сначала отличить от устаревшей цены.** Запрос из раздела выше, со словом из
названия. Другой товар в паре — когда у сайта две строки с (почти) одним
названием, обе виденные недавно, с РАЗНЫМИ ценами и разными номерами кластера,
и цена соседней строки совпадает с ценой конкурента из жалобы. Если строка у
сайта одна, а её цена не та, что на сайте, — это сбор: смотреть `seen` и
«Расписание сбора» (у pharmonline между недельными сборами цены не обновляются
вовсе, а упавший сбор оставляет их ещё на неделю; ⚠️ с правки 2026-10-13 сбор
ежедневный — раздел «Ежедневный сбор: что стоит на сервере», и устаревшая цена
— это вчерашняя, если ночной сбор прошёл).

**Что делает этап сопоставления** (с правки 2026-10-13; на сервере — после
выкладки и прогона этапа):

- подготовительный шаг `replace_price_strangers` (третий, после замены
  устаревших строк; в выводе `rematch` — `Price strangers reseated: N`) меняет
  в кластере товар, чья цена расходится с каждым другим членом, на его соседа
  по сайту с их ценой. Сосед без пары занимает место; сосед из другого кластера
  меняется с заменяемым местами, переходит один или — если он у себя на месте —
  принимает остальных в свой кластер. В журнале этапа —
  `matcher_price_strangers_replaced`: для каждой замены кластер, где товары
  теперь стоят вместе с соседом (`match_id`), кто вышел (`old`, `old_price`),
  сосед (`new`, `price`), кластер, который покинул сосед, а при `joined` —
  остальные (`from_match`, номер или пусто), был ли это обмен двух товаров
  местами (`swapped`), кто перешёл к соседу (`joined`) и кого оставил без пары
  распущенный кластер (`left_alone`). Название кластера, которое после ухода
  товара не носит никто из оставшихся, шаг заменяет названием оставшегося.
  Сбой шага этап не останавливает: его записи откатываются к точке сохранения,
  сессия сбрасывается, проходы идут с прежними парами — но `rematch` тогда
  выходит с ошибкой `preparation step failed: reseated`, а в ночном сборе след
  один: строка `matcher_preparation_failed` в журнале;
- проходы из двух одинаково похожих по названию товаров сайта берут тот, у
  которого цена та же (`_closest_first`), и не отдают кандидата якорю с другой
  ценой, когда рядом стоит так же близкий товар с ценой кандидата;
- «laktat» — слово варианта (`_VARIANT_WORDS`): «Ringer laktat» и «Ringer» в
  одну пару не входят, существующую пару распускает `revalidate_split` с
  постоянным отказом `revalidate-split`.

Что шаг сделал бы сейчас, не меняя базу:

```bash
# на сервере, под pm, с загруженным env; печатает список и выходит
cd /opt/pharmacy-monitor && sudo -u pm bash -c 'set -a; . /etc/pharmacy-monitor/env; set +a;
  .venv/bin/python -B -c "
from src import matcher, storage
with storage.make_session()() as s:
    for item in matcher.replace_price_strangers(s, dry_run=True):
        print(item)
    s.rollback()"'
```

Как и команда из раздела выше, она берёт транзакционный замок сопоставления —
запускать, когда прогона в работе нет. Проверена на копии базы 2026-10-13
(около пяти секунд); на сервере работает после выкладки правки (до неё такого
шага в коде нет). Вместе со списком она печатает события
`matcher_price_stranger_kept` (уровень debug, в журнале юнита их нет): сосед с
ценой остальных нашёлся, а пара оставлена. Причины (`reason`):

- `several_siblings` — таких соседей несколько;
- `prices_agreed_before` — по журналу цен заменяемый раньше стоил, как кто-то из
  остальных (в том числе как товар, которого сейчас нет в наличии): пара была
  верной, изменилась цена. Время записи не сверяется: достаточно, чтобы один
  когда-то носил цену, которую носил или носит другой;
- `sibling_cluster_not_to_be_touched` — сосед стоит в ручном кластере, в
  кластере с двумя строками одного сайта или рядом со строкой сайта, который
  давно не собирался;
- `sibling_agrees_with_its_cluster` — сосед у себя на месте (сходится в цене
  сейчас или сходился раньше), а остальные в его кластер не подходят.

На копии каталога событие одно: «Almagel A» aloe стоит с «Almagel» двух сайтов,
а «Almagel» aloe — в ручной паре с «Almagel A» aptekonline; такую пару правит
оператор.

**Когда шаг товар не меняет** — намеренно. Условия самого шага закреплены
тестами (`tests/test_matcher_coverage.py`, от «Цена как признак одного товара»
до конца); из правил проходов тестом закреплено, что шаг их спрашивает с каждым
членом кластера, а сами правила — не все (модификатор, форма и форма по соседям
закреплены, длина названия и гендер — нет):

- цена расходится меньше чем на 1%, или член кластера близок по цене хотя бы
  к одному из остальных: два листинга одного товара, переставлять незачем;
- раньше, по журналу цен, заменяемый стоил, как кто-то из остальных: это
  изменение цены, а не чужой товар;
- у остальных членов цена не одна — под какую искать замену, неясно;
- на сайте нет товара с ценой остальных (совпадение — до 0,5%) или таких два;
- сосед дальше по названию от кого-то из остальных, чем заменяемый, или
  проходы его кому-то из них запрещают (`_PassRules.incompatible` — те же
  правила, что у `blocked`: страна, состав, доза и порядок доз, форма,
  модификатор, отказы оператора и системные; ещё цена за единицу);
- у заменяемого страна подтверждена, а у соседа она другая или неизвестна:
  страна — часть идентичности, цена её не перевешивает;
- сосед пропал с сайта, не в наличии, без цены, с мёртвой ссылкой;
- кластер ручной или в нём две строки одного сайта — и тот, где меняют, и тот,
  откуда пришлось бы забрать;
- в кластере есть давно не виденная строка сайта, у которого полный сбор не
  проходил: «не собран» — не «пропал», о такой строке неизвестно ни цены, ни
  продаётся ли товар. Пока сайт не собран, его пары шаг не трогает;
- сосед стоит в другом кластере и там на месте, обмен местами не подходит, а
  остальные в его кластер не подходят (общий сайт, отказ, правило проходов,
  цена, название или страна — мерка здесь сам сосед).

**Чего это не чинит.**

- Пары, где названия различаются, цены тоже, а соседа с той же ценой нет: цена
  там ничего не доказывает, и шаг их не трогает. Замер по рассылке 2026-10-11
  (83 алерта «конкурент дешевле на 10% и больше»): пара исправлена под шестью —
  это все четыре товара из жалобы и «Selestoderm V»; из остальных 77 у 43
  названия на сайтах совпадают, у 34 различаются.
- Неверные пары с РАВНОЙ ценой: на копии «Triderm krem 15 q» aloe стоит с
  «Triderm 15 qr (Məlhəm)» клиента, оба по 9,32. Шаг смотрит только на тех, чья
  цена расходится.
- Пару, которую проходы неверно собрали в этом же прогоне: шаг идёт до
  проходов и исправит её в следующем. Алерт по ней один раз уйти успеет.
- Товар, оставшийся после замены без пары (свечи, лимонный), новую пару
  получит, только если у конкурента есть его товар и правила названий его
  пропускают: «Septolete total limon və ağcaqayın» клиента и «…limon, kəndalaş»
  aptekonline остаются врозь — добавочные слова разные.
- Неверную пару, члены которой когда-то носили одну цену в разное время:
  журнал цен сверяется без учёта времени и такую замену запрещает. Отказ
  оставляет пару как была; обратной ошибки — подмены товара из-за настоящего
  изменения цены — журнал не допускает.

**Что меняется попутно.** Товар клиента, перешедший в другой кластер или
оставшийся без пары, меняет номер кластера: ключ повтора алертов содержит
номер, и у старых событий на странице алертов пропадает ссылка на товар (как у
слияний из раздела выше; на копии таких товаров клиента пять). Закупочные цены
и остатки, привязанные к кластеру, при переходе остальных к соседу идут с ними;
у кластера, распущенного потому, что в нём остался один товар, уходят каскадом
(обе таблицы на проде 2026-10-07 были пусты — проверить перед прогоном:
`select count(*) from stock_levels where canonical_id is not null` и то же для
`supplier_prices`).

**Перед первым прогоном на сервере** — команда «что шаг сделал бы сейчас»:
список должен быть близок к замеру из PR (на копии от 2026-10-12 — 14 замен,
товары названы в описании PR #97). Совпасть до строки он не обязан: замер снят
с копии, а цены и наличие на сайтах с тех пор менялись — замена могла пропасть
или прибавиться. Если расхождение этим не объяснить — замен заметно больше,
товаров из замера в списке нет, — этап не запускать и показать список
владельцу.
И два счёта: `select count(*) from stock_levels where canonical_id is not null` и
то же для `supplier_prices`. Если не ноль — остановиться и показать владельцу:
роспуск кластера удалит привязанные к нему строки.

Первый прогон на сервере прошёл 2026-10-13: замен тоже 14
(`Price strangers reseated: 14` в сохранённом выводе `rematch`; сошлось число,
состав списка при этой правке не сверяли). После него 14 — уже не мерка: на
копии второй прогон ничего не менял, а на живой базе новые замены могут
появляться по мере того, как меняются цены, наличие и каталог.

**Откат.** Как у слияний из раздела выше, со снимком самих пар: распущенный
кластер удаляется, и возврат товара в него упирается во внешний ключ. Шаг
отката тот же («Откат слияний»), и в ту же транзакцию, перед `commit`, — ещё
две команды. Первая снимает отказ, записанный при роспуске пары «Ringer
laktat» — «Ringer»: сам он не уйдёт, а с ним пара не вернётся (`:r` —
сохранённый `max(id)` из `match_rejections`). Вторая возвращает названия
кластеров, которые шаг сменил:

```sql
update match_rejections set is_active = false where id > :r and reason = 'revalidate-split';
update matches m set canonical_name = b.canonical_name, canonical_brand = b.canonical_brand,
       canonical_dosage = b.canonical_dosage, canonical_pack_size = b.canonical_pack_size
  from matches_before b
 where m.id = b.id and (m.canonical_name, m.canonical_brand, m.canonical_dosage, m.canonical_pack_size)
       is distinct from (b.canonical_name, b.canonical_brand, b.canonical_dosage, b.canonical_pack_size);
```

На копии базы 2026-10-13 после этапа с 14 заменами и одним роспуском это
вернуло назначения всех товаров, все 4 898 пар с их названиями (сменившихся
было четыре) и число действующих отказов. Не вернулась уверенность
(`confidence`) у одной пары — её этап меняет и без этой правки. Первая команда снимает все отказы
`revalidate-split`, записанные после выкладки, — не только этот. Если между
выкладкой и откатом прошли сборы, сначала посмотреть список
(`select * from match_rejections where id > :r`).

Недельный сбор pharmonline запускает cron GitHub (понедельник 03:20 UTC), а не
таймер сервера: шаг 1 отката его не останавливает, и код он берёт из `main`.
Откат данных и возврат `main` не разносить через это время — иначе сбор
выполнит новый код на возвращённых данных. (⚠️ С правки 2026-10-13 этого cron

### Замок сопоставления потерян посреди этапа

**Симптом** — в журнале PostgreSQL, а не приложения:

```bash
zgrep -h "you don't own a lock" /var/log/postgresql/postgresql-16-main.log*
```

Строка через несколько секунд после `matcher_done` в журнале сбора значит, что
этап сопоставления снимал замок, которого у него уже не было. Этап (конец `run`,
`rematch`) держит сессионный advisory-замок `pharmacy_monitor_matcher` и под ним
делает несколько транзакций. До 2026-10-08 замок брался запросом через обычную
сессию, а она после каждого commit возвращает соединение в пул. Соединение
старше `DB_POOL_RECYCLE` (30 минут) пул на следующей выдаче закрывает — вместе с
замком. Дальше этап шёл без него, и правка пары из дашборда, ждавшая замок,
проходила между `match_products` и `revalidate_split`.

Замер 2026-10-08 по журналам прода: так кончились 12 этапов из 39 с 3 сентября
по 7 октября — ровно те, у которых тридцатая минута процесса пришлась между
взятием замка и commit `match_products` (у aloe 12 из 30: его сбор длится
полчаса). Тридцатая минута процесса — приближение: пул считает возраст
соединения, а сессия открывает его в первые секунды команды. Ручных правок пар за это время не было вовсе — ни одного ручного
отказа в `match_rejections`, ни одного запроса на изменение пар в журнале
Caddy, — так что в окно никто не попал.

Теперь замок берётся на отдельном соединении вне пула, и до снятия сессия этапа
работает только через него (`matcher.acquire_match_mutation_lock`). Правка
(PR #56) действует на сервере только после выкладки — сначала проверить её:

```bash
grep -c _HeldLock /opt/pharmacy-monitor/src/matcher.py
```

`0` — на сервере прежний код, и строка в журнале PostgreSQL — та самая потеря
замка: событий в журнале сбора при ней нет и не будет. Лечится выкладкой
(`deploy.yml`), порядок любой: старый и новый код берут один и тот же замок и
друг друга исключают.

Если правка выложена, новых строк быть не должно. Появилась:

- в журнале сбора рядом будет `matcher_lock_not_held_at_release` или
  `matcher_lock_release_failed` — по времени найти прогон и смотреть, что
  случилось с соединением (перезапуск PostgreSQL, обрыв);
- если этих событий нет — замок снимает кто-то мимо общих функций: искать
  `pg_advisory_unlock` в `src/` и `scripts/`.

**Этап оборвался посреди работы** — отказом `the session is no longer on the
connection that holds the match mutation lock` (соединение замка потеряно) или
любой другой ошибкой после `matcher_done`. К этому моменту `match_products`
свои пары уже зафиксировал, а `revalidate_split` мог не пройти: в базе могут
остаться пары, которые текущие правила запрещают. Раньше обрыв соединения
между шагами проходил молча, теперь это отказ. Что сделать:

1. Повторить этап: `pharmacy-monitor rematch` без флагов (как запускать на
   сервере — «Выкладка правок сопоставления» ниже). Он доделает `revalidate`.
2. Проверить статус прогона: `select id, status, error_message from runs order
   by id desc limit 3`. После ошибки SQL посреди этапа прогон закрывается как
   `failed` с причиной: обработчик сбоя откатывает транзакцию — соединение
   замка при этом закрывается — и пишет итог. На коде без `_persist_chunks`
   (`grep -c _persist_chunks /opt/pharmacy-monitor/src/main.py` даёт 0)
   обработчик падал сам, и прогон оставался в `running` — см. «В журнале сбора
   `incremental_persist_failed`…».

Кто держит замки сбора и сопоставления прямо сейчас:

```bash
sudo -u postgres psql -X pharmacy_monitor -c "
  select case l.objid::bigint
           when hashtext('pharmacy_monitor_matcher')::bigint & 4294967295 then 'сопоставление'
           when hashtext('pharmacy_monitor_scrape')::bigint & 4294967295 then 'сбор'
           else l.objid::text end as lock,
         l.pid, l.granted, a.state, a.xact_start, left(a.query, 60) as query
  from pg_locks l join pg_stat_activity a using (pid)
  where l.locktype = 'advisory'"
```

Замок сбора всю команду лежит на соединении в состоянии `idle` без
`xact_start` — это штатно. Замок сопоставления держит то же соединение, через
которое этап пишет: строка одна, `pid` у замка и у запросов этапа совпадает.
Строка с `granted = f` — кто-то ждёт: правка пары из дашборда во время этапа.

Когда этап закончился (после `matcher_done` идут ещё `revalidate_split` и флаги
цен), тот же `pid` может какое-то время числиться держателем. Это уже не замок
этапа, а транзакционный замок `revalidate_split`: когда разбивать нечего, он
не фиксирует транзакцию, и замок живёт до следующего commit
команды (в сборе с `--limit` он держался ещё во время анализа прогона). Правка
пары всё это время тоже ждёт. Так было и до 2026-10-08.

### Текущая стратегия

> ⚠️ Список ниже и раздел «Восстановление из бэкапа» — времён SQLite, устарели
> (помечено 2026-10-07). Сейчас: Postgres, `pg_dump` каждую ночь в 04:00 по
> времени сервера, `/var/backups/pharmacy-monitor/`, хранение 14 дней — см.

- **Когда:** ежедневно в 02:00 UTC (`pharmacy-monitor-backup.timer`)
- **Где:** `/opt/pharmacy-monitor/data/backups/db-YYYY-MM-DD.sqlite.gz`
- **Срок хранения:** 90 дней
- **Размер:** ~200KB на ~1MB БД (gzip −80%)

### Восстановление из бэкапа

```bash
# 1. Остановить процессы которые пишут в БД
sudo systemctl stop pharmacy-monitor-dashboard
sudo systemctl stop pharmacy-monitor-telegram
sudo systemctl stop pharmacy-monitor-run.timer

# 2. Сделать копию текущей БД (на всякий случай)
sudo -u pharmacy cp /opt/pharmacy-monitor/data/db.sqlite \
  /opt/pharmacy-monitor/data/db.sqlite.before-restore

# 3. Распаковать выбранный бэкап
sudo -u pharmacy gunzip -c /opt/pharmacy-monitor/data/backups/db-2026-04-29.sqlite.gz \
  > /opt/pharmacy-monitor/data/db.sqlite

# 4. Проверить integrity
sudo -u pharmacy sqlite3 /opt/pharmacy-monitor/data/db.sqlite "PRAGMA integrity_check;"

# 5. Запустить процессы обратно
sudo systemctl start pharmacy-monitor-dashboard
sudo systemctl start pharmacy-monitor-telegram
sudo systemctl start pharmacy-monitor-run.timer
```

### Сделать бэкап вручную

```bash
# Postgres pg_dump → /var/backups/pharmacy-monitor/ (+ GPG если задан BACKUP_GPG_PASSPHRASE,
# + B2 offsite если заданы B2_APPLICATION_KEY_ID/KEY):
sudo systemctl start pharmacy-monitor-backup.service
# или напрямую: sudo bash /opt/pharmacy-monitor/infra/scripts/backup.sh
```

### Копия бэкапа вне сервера

Сервер хранит 14 дней дампов только на собственном диске. B2 не настроен
(`B2 upload skipped` в journald сервиса), других заданий, уносящих дамп наружу,
на сервере нет. **На 2026-10-07 копии вне сервера нет.** Наружу дамп уходит
только вручную:

```bash
bash infra/local/fetch-backup.sh --list   # что лежит на сервере
bash infra/local/fetch-backup.sh          # забрать свежий в ~/Backups/pharmacy/
```

Запускать с машины, чей SSH-ключ принимает сервер (сейчас это dev-бокс). Он
тоже стоит у Contabo: копия там переживёт потерю машины, но не аккаунта —
настоящая внешняя копия должна лежать ещё где-то. Скрипт предупредит, если
ночной бэкап пропустил хотя бы одну ночь (самый свежий файл на сервере —
позавчерашний или старше): однажды он уже месяц молча падал.
Дамп зашифрован `BACKUP_GPG_PASSPHRASE` из `/etc/pharmacy-monitor/env`: без
копии этого пароля вне сервера забранный файл не расшифровать. Проверять
расшифровкой до конца, а не наличием файла (команда молча ждёт пароль на stdin:
ввести его и нажать Enter; обрезанный файл даст ошибку, а не «дамп цел»):

```bash
gpg --batch --yes --passphrase-fd 0 -d <файл>.sql.gz.gpg | gunzip -t && echo "дамп цел"
```

Проверка паролем, прочитанным с сервера, доказывает только целость дампа. Что
пароль есть и вне сервера, она не доказывает — а на 2026-10-07 это не
установлено.

Восстановление — в отдельную пустую базу, не в боевую. На этом сервере оно ни
разу не проверялось, команды ниже собраны по тому, как устроен дамп:

```bash
# НЕ направлять в pharmacy_monitor: дамп сделан с --clean и начинается с удаления
```

## 🔄 Обновления / деплой нового кода

### Сборка интерфейса отдельно от работающей версии (2026-10-16)

В актуальном `deploy.yml` интерфейс собирается в приватном каталоге
`.deploy-stage.*/runtime/frontend` **до миграции и замены живого кода**. Ошибка
установки зависимостей, сборки или проверки готового standalone на этапе сборки оставляет базу,
код и работающий интерфейс прежними. Исходники проверяются по SHA-256; настройки
из существующих production `.env*` копируются приватно, без вывода значений.

Готовая сборка переезжает в
`/opt/pharmacy-monitor/.frontend-releases/<sha>-<run>-<attempt>/.next`, а
`/opt/pharmacy-monitor/frontend/.next` становится ссылкой на неё. После
переключения workflow перезапускает API и интерфейс и проверяет HTTP. Первый
переход с обычной папки сохраняет её как `previous-<run>-<attempt>`; следующие
выкладки атомарно заменяют ссылку. `DEPLOYED_SHA` внутри `.next` содержит SHA
релиза. Статические файлы и `public/` входят в standalone.

Не запускать `pnpm build` в живом `frontend`: Next очищает `.next`, а работающий
сервер пишет туда кэш. В Next 14.2.18 повтор удаления непустой папки может стать
бесконечным. Сборка в отдельном каталоге устраняет это пересечение. Удаление
`.deploy-stage.*` после выкладки не затрагивает опубликованные поколения.
Автоматической очистки `.frontend-releases` пока нет: контролировать свободное
место; старые поколения нельзя удалять, пока на них ссылается `.next` или их
использует процесс. Это сохранение файлов, а не разрешение откатывать базу или
выкладывать старый workflow.

- в режиме watchlist — его зовёт `watchlist-tick`, как только в списке
  появится хотя бы одна подтверждённая ссылка (2026-10-07 их нет, тик выходит
  сразу).

Не доходят: `intraday-tick` и `scrape` (только сбор цен), пустой
`watchlist-tick`, упавший или не прошедший проверку полный сбор. Поэтому после
выкладки новые пары сами появятся лишь с ближайшим сбором, дошедшим до этапа, —
обычно в понедельник. Их создаёт шаг «После выкладки» ниже.

Если правила сопоставления в этих двух копиях разные, они портят работу друг
друга: новый код создаёт пару, старый `revalidate_split` в конце следующего
сбора или планового `rematch` считает её конфликтом, распускает и пишет
постоянный отказ в
`match_rejections` (`reason_type` `system_spec`). Отказ переживает выкладку —
пара не вернётся, пока его не снимут. Так было бы, например, с Veqovi: старое
правило дозы видит «0.25 mq (0.68 mq/ml)» и «0.25 mq/doza 1 mq» как разные дозы.

**Перед выкладкой** — снять состояние сопоставления и унести его с сервера
(ночной бэкап лежит на том же хосте):

```bash

```

```bash
sudo -u postgres psql -X -At pharmacy_monitor -c "select 'matches', max(id) from matches union all select 'match_rejections', max(id) from match_rejections union all select 'match_policy_audits', max(id) from match_policy_audits"
```

И сами пары — без них откат не выполнить (с 2026-10-12 этап удаляет записи
кластеров: при слиянии двух кусков одного товара и при замене чужого по цене):

```bash
sudo -u postgres psql -X pharmacy_monitor -c "\copy (select * from matches) to '/tmp/pm-matches-before.csv' csv"
```

И бэкап базы до запуска этапа: `deploy.yml` без `apply_migrations` его не
делает.

```bash

```

**После выкладки** — запустить этап сопоставления самим, под пользователем и с
окружением сервиса, и сверить с замером из PR. Сначала убедиться, что сбор не
идёт (`select id, status from runs where finished_at is null` — пусто), и не
попадать в первые минуты часа: с 05 до 17 по времени хоста в это время идёт
дневной тик, и занятый замок заставит его пропустить свою очередь.

```bash

```

Без флагов. Команда выполняет тот же этап, что конец сбора
(`main._run_matching_stage`): пересчёт выводимых полей, замена устаревших строк
живыми двойниками, замена чужих по цене их соседями по сайту (с 2026-10-13),
сопоставление, `revalidate_split`, флаги цен. Пары она не сбрасывает; уже
сделанные назначения меняют только две эти замены и
`revalidate_split` (выводит товар не в наличии и распускает пары, которые
запрещают текущие правила), а товары без пары присоединяются к существующим
кластерам как обычно. В выводе: `Products re-normalized`,
`Stale members relinked`, `Price strangers reseated` (с 2026-10-13: замена
чужого по цене члена кластера его соседом по сайту), `Matcher done`,
`Revalidate`, `Price-spread flags`.
Ненулевой код выхода — упал шаг подготовки (в выводе `FAILED, see log`) или
revalidate; стек — в выводе этой команды (у юнита — в journald). `FAILED` только в строке флагов цен кода выхода
не меняет. Пока замок сбора занят — идёт сбор, тик, другой `rematch` или
служебная команда, — команда отвечает `skipped because the run lock is busy`
(код 0): повторить позже. Первый полный сбор после выкладки пришлёт одно письмо
с алертами по всем новым парам, где конкурент дешевле, — это ожидаемо.

**`rematch --reset` на проде не запускать.** Он удаляет все автоматические пары
и собирает их заново. Без второго флага `--i-accept-full-rebuild` команда
откажет, ничего не тронув (код 2). Отказ живёт в коде и действует на сервере
только после выкладки `deploy.yml`. Второй путь к тому же сбросу —
`scripts/full_rematch.py`: в репозитории он требует тот же флаг, но каталог
`scripts/` выкладка не возит, и 2026-10-07 на сервере лежала копия от 2026-07-13

- меняются номера всех пар: с парой каскадом удаляются привязанные к ней строки

  CASCADE`, проверено 2026-10-07; обе таблицы пока пусты), записи
  `match_policy_audits` остаются с номером несуществующей пары, а ключ

  названия с частым первым словом (гигиена, косметика), где теперь нужно полное
  совпадение слов; 31 — товар одинаково подходит к двум строкам конкурента с

Что сброс делал неявно и чего без него нет: новые правила прохода (`blocked`,
неоднозначность, выбор ближайшего) применялись и к старым парам.
`revalidate_split` перепроверяет у существующих пар только
`_pairwise_spec_conflict` и наличие. Поэтому правило, которое должно убрать уже
существующие пары, либо добавляют в `_pairwise_spec_conflict`, либо выкладывают
вместе с разовой чисткой; а расхождение «с нуля» против текущего состояния
полезно время от времени мерить на копии каталога.

**Юнит `pharmacy-monitor-rematch`** (вторник и пятница 04:30 по времени хоста —
после недельных сборов понедельника; два дня, потому что пропуск при занятом
замке никто не повторяет) лежит в `infra/systemd/` и зовёт `rematch` без флагов.
На проде с 2026-05-26 стоит положенный руками юнит с `--reset` (понедельник
05:00 по времени хоста) — сброс шёл каждую неделю. **Стоит ли он до сих пор,
показывает только сервер**: `systemctl cat pharmacy-monitor-rematch.service |
grep ExecStart`. `deploy.yml` юниты не ставит. Что будет в понедельник:

- код не выложен — старый юнит выполнит сброс, как раньше;
- код выложен, юнит старый — команда откажет с кодом 2, пары не тронет; юнит
  будет числиться упавшим, уведомлений об этом нет;
- код выложен и юнит заменён — юнит в понедельник не запускается, плановые
  прогоны идут во вторник и пятницу.

Выложен ли код с отказом: `grep -c -- '--i-accept-full-rebuild'
/opt/pharmacy-monitor/src/main.py` — 0 значит «нет».

Заменить юнит — от root, после выкладки (файлы появляются в
`/opt/pharmacy-monitor/infra/systemd/` вместе с ней) и после ручного прогона из
шага «После выкладки»:

```bash
d=/root/pharmacy-monitor-rematch-unit-$(date +%F-%H%M) && mkdir "$d" && cp -a /etc/systemd/system/pharmacy-monitor-rematch.service /etc/systemd/system/pharmacy-monitor-rematch.timer "$d"/ && install -m 0644 /opt/pharmacy-monitor/infra/systemd/pharmacy-monitor-rematch.service /opt/pharmacy-monitor/infra/systemd/pharmacy-monitor-rematch.timer /etc/systemd/system/ && systemctl daemon-reload && systemctl restart pharmacy-monitor-rematch.timer && systemctl cat pharmacy-monitor-rematch.service | grep ExecStart
```

В ответ — одна строка `ExecStart=… pharmacy-monitor rematch`, без `--reset`.
Расписание — `systemctl list-timers pharmacy-monitor-rematch.timer`: ближайший
запуск во вторник или пятницу в 04:30, не в понедельник.
Таймер с `Persistent=true` после смены расписания может сработать сразу — это
тот же `rematch` без флагов; его вывод — в
`journalctl -u pharmacy-monitor-rematch.service`. Поэтому ручной прогон делают
до замены юнита: иначе первым этапом после выкладки станет прогон без
присмотра, а ручной в это время ответит `run lock is busy`. На новом хосте, где
прежних файлов нет, юнит ставит `infra/scripts/install_systemd_schedule.sh`; он
же откажет, если systemd всё ещё собирается запускать `--reset` (местный
drop-in).

**Откат — сначала данные, потом код.** Просто вернуть код нельзя: старый
`revalidate_split` начнёт распускать новые пары с постоянными отказами.

1. Остановить таймеры (`systemctl list-timers 'pharmacy-monitor*'`, затем
   `systemctl stop` для scrape/intraday/watchlist/rematch и для
   `pharmacy-monitor-scrape-watcher.timer` — кнопка в дашборде тоже доходит до

2. Пока на сервере новый код, вернуть назначения из снятых файлов. **С

   Он годится и когда ничего не удалялось: вставка даст ноль строк.

   Блок ниже не выполнять: это прежний вариант, без снимка пар. Если этап
   после выкладки удалял записи кластеров — при слиянии, замене по цене или
   роспуске пары в `revalidate_split`, — он упрётся во внешний ключ. Оставлен

### Идентификаторы aloe: номер товара

С миграции `0024_aloe_product_numbers` товар aloe в `products` узнаётся по
номеру товара на сайте (`external_id = '12058'`), адрес —
`https://aloe.az/12058/#ceftriaxone-1-q`. Раньше идентификатором был слаг, а
слаг сайт сам даёт нескольким разным товарам: они писались одной строкой.
Почему номер, а не слаг и не `code`, — в шапке `src/scrapers/aloe.py`.

**Правило включает миграция, а не выкладка кода.** Миграция ставит на
`products` триггер `products_aloe_number_identity`. Пока его нет, код пишет
товары aloe под слагом, как раньше; когда он есть — под номером. Строки
миграция не трогает: строку, записанную под слагом, переводит на номер сама
запись сбора, когда сбор снова видит товар (`main._adopt_aloe_product_numbers`,
событие `aloe_product_numbers_adopted`).

Кому достаётся строка общего слага, решает только **полный сбор aloe,
которому система верит** (все разделы пройдены, качество прогона в норме —
прогон кончается `ok`): он видит все товары слага, а решение необратимо. Тик и сбор раздела
переводят строку, только когда пришедший товар в ней и записан (совпали
страна, бренд и последняя цена — всё, что в строке есть); остальные товары,
пока строка свободна, до полного сбора не пишутся вовсе (`left_for_full_scan`,
номера — в `waiting`).

**Включение правила — по шагам:**

1. До выкладки (только чтение). Слага из одних цифр в каталоге нет — он был бы
   принят за номер; закреплённых ссылок aloe нет; PR #52 закрыт; PR #39 смержен
   (он убирает workflow, которые кладут на сервер файлы по одному: прежний
   `src/main.py` при новом сборщике до первого полного сбора завёл бы вторые
   строки, и предохранитель этого не видит):

```sql
select external_id from products where site = 'aloe' and external_id ~ '^[0-9]+$';  -- только '0'
select count(*) from tracked_product_links where site = 'aloe' and url is not null;  -- 0
```

4. Проверить: прогон кончился `ok` (`select id, status, catalog_verified from

   вывода команды `whole_catalog=True` и `left_for_full_scan=0`, запрос 2 ниже

   слагов он не назначал; ближайшей ночью плановый сбор повторит попытку сам,

```bash

  -u pharmacy-monitor-intraday --since today -g aloe_product_numbers_adopted -o cat"
```

В событии: `products` — сколько строк переведено; `whole_catalog` — решал ли
полный сбор; `shared_slugs` — у скольких слагов со строкой сбор видел больше
одного товара; `left_for_other_country` — сколько строк остались под слагом,
потому что все пришедшие товары слага другой страны (каждый получил свою
строку); `left_for_full_scan` и `waiting` — сколько и какие товары частичный
сбор не записал и оставил полному.

```sql
-- 0. Правило включено? (true — предохранитель стоит и не отключён)
select exists (select 1 from pg_trigger
                where tgname = 'products_aloe_number_identity' and tgenabled <> 'D');

-- 1. Сколько строк под номером и сколько осталось под слагом.
select count(*) filter (where external_id ~ '^[0-9]+$' and external_id <> '0') as under_number,
       count(*) filter (where external_id !~ '^[0-9]+$' or external_id = '0')  as under_slug
  from products where site = 'aloe';

-- 2. После первого ПОЛНОГО сбора: строки под слагом, у слага которых уже есть
--    строка под номером, виденная после включения правила. Их должно быть
--    столько, сколько `left_for_other_country` в событии этого сбора (строка
--    оставлена, потому что пришедшие товары другой страны). Больше — сбор
--    наследников не назначал или не дошёл до этих товаров.
select count(*) from products s
 where s.site = 'aloe' and (s.external_id !~ '^[0-9]+$' or s.external_id = '0')
   and exists (
       select 1 from products n
        where n.site = 'aloe' and n.external_id ~ '^[1-9][0-9]*$'
          and n.url like '%/#' || split_part(rtrim(s.url, '/'), '/', 4)
          and split_part(n.url, '#', 2) = split_part(rtrim(s.url, '/'), '/', 4)
          and n.last_seen_at > timestamp '<время включения, UTC>');

-- 3. Слаги, под которыми теперь несколько строк, — те самые разные товары.
select split_part(url, '#', 2) as slug, count(*), array_agg(external_id order by id)
  from products where site = 'aloe' and url like '%#%'
 group by 1 having count(*) > 1 order by 2 desc limit 20;

-- 4. Должно быть пусто: номер в идентификаторе при адресе без номера
--    (строку под номером завёл или затёр `ai-crawl`).
select id, external_id, url from products
 where site = 'aloe' and external_id ~ '^[1-9][0-9]*$'
   and url not like 'https://aloe.az/' || external_id || '/%' limit 20;
```

Что увидит клиент в первом полном сборе после включения: товары, которые
раньше были скрыты за чужой строкой (2026-10-08 таких в продаже около 190),
придут как «новые», а у единичных строк, где лежала цена другого товара, цена
«изменится» на правильную (на копии каталога — одна строка в парах:
`lavanda-yagi-10-ml`, 7,3 → 2,8).

**Сбор aloe падает с «already stored under its site number».** Сработал
предохранитель: в базу пишет код, который о номере не знает (выложена старая
ветка, обходной workflow положил прежний `src/main.py`, сбор запущен из
старого чекаута). Он ищет товар по слагу, не находит переведённую строку и
вставляет вторую — предохранитель вставку отвергает, строк не прибавляется.
Чинить код на сервере (`deploy.yml --ref main`), а не базу: сверить
`sha256sum /opt/pharmacy-monitor/src/main.py` с `git show origin/main:src/main.py`.
Триггер руками не снимать и не отключать.

**Сбор aloe падает с «уже записаны под номером, а правило выключено».**
Предохранителя в базе нет (снят руками, потерян при пересоздании таблицы или
при загрузке одних данных), а строки уже под номером. Запись под слагом завела
бы каталог второй раз, поэтому код отказывает. Вернуть предохранитель — шаг
`upgrade` (команда ниже, `m.upgrade()`).

### Aptekonline: временный HTTP 403 и неполный каталог (2026-10-20)

В `Run.run_quality.sites.aptekonline.routes_incomplete` причина
`hard_block_403` означает, что запрос категории получил HTTP 403. Она сама по
себе не доказывает ни исчерпание баланса, ни исчезновение категории. В инциденте
20 октября у прогона1091 отказали20категорий; в повторе1092 все они ответили,
но отказала другая категория233, которая в1091 дала1250товаров. Количественный
порог проходил, однако полный каталог правильно не был подтверждён.

Для настроенного Decodo HTTP403 теперь допускает новый **цельный** проход
категории с другой настроенной sticky-сессией. Бюджет — не больше меньшего из
`APTEKONLINE_CATEGORY_ATTEMPTS` (по умолчанию3) и числа настроенных сессий;
одна сессия не даёт дополнительного повтора. Сам403 не расширяет бюджет до
всего пула и не включает отложенное восстановление усечённого ответа200.
Причина403 сохраняет название `hard_block_403`; если полную категорию получить
не удалось, в результате остаётся лучшая неполная попытка и её причина.
Данные разных попыток не объединяются.

HTTP401/451 остаются немедленным отказом категории;402/407 — отказом
прокси-доступа, который прекращает сбор сайта. Прямой маршрут и прочие
провайдеры сохраняют прежнее поведение. Нового автоматического переключения
между провайдерами нет.

При разборе проверять последнюю подтверждённую эпоху, причины неполноты и
конкретные категории двух попыток. `items_completed` и высокий процент
количественного покрытия недостаточны: вся пагинация каждой категории должна
пройти проверку. Точечное чтение первой страницы показывает доступность API,
но не является полным сбором и не снимает тревогу. Увеличение порога свежести,
объявление частичного каталога полным или перенос старых цен в новую эпоху
не являются восстановлением.

После штатной выкладки подтверждать новый полный Aptekonline run со
`catalog_verified=true`, `financially_eligible=true`, без `routes_incomplete`,
а затем свежесть каталога и сравнения цен. Не считать эту правку доказанным
восстановлением до такого прогона. Изменение без миграции; возврат кода — revert
через проверенный PR и штатный deploy.yml, без изменения истории цен.

### DDP recovery procedures

**`catalog_verification_reason=pending` + failed full run**:
- прогон оборвался до проверки каталога. Само значение `pending` не отличает
  DDP startup от более позднего исключения до verification; `site_drop` при
  этом является следствием старых данных, а не причиной падения;
- для run `#656` публичный `/health` не содержит `error_message`, поэтому точную
  причину брать только из строки Run или journal. Исторический run `#629` падал
  на `timed out during opening handshake`, но это лишь диагностическая гипотеза
  для `#656`, пока не прочитан его собственный error;
- сначала посмотреть сохранённый `Run.error_message` и
  `journalctl -u pharmacy-monitor-scrape@pharmonline.service --since '9 days ago'`;
- проверить только безопасные признаки конфигурации: что `pharmonline` входит в
  `DECODO_SITES`, заданы оба credential-поля, доступны все порты из
  `DECODO_PORTS`, а в аккаунте Decodo есть баланс. Значения credentials не
  печатать и не передавать в issue/log;
- HTTP 402/407 означает баланс/credentials: исправить аккаунт/config и выполнить
  один штатный full run. Таймаут после перебора всех sticky-портов означает
  проблему WebSocket tunnel/exit pool; не маскировать её повышением health-порога;
- восстановление подтверждено только когда full run имеет `status=ok`,
  `catalog_verified=true`, а `MAX(products.last_seen_at)` для pharmonline свежий.

Startup timeout/OSError/402/407 теперь превращается в sanitized
`SiteScrapeFatalError: DDP startup failed: ...` без исходной exception-chain
(`raise ... from None`). Это важно: proxy-библиотека может включить сырой URL с
credentials в исключение, а `run_cmd` печатает traceback через `log.exception`.
`scrape_site` перехватывает этот тип и возвращает структурированный
`ScrapeResult(site_fatal=true)`, поэтому параллельный успешный сайт не отменяется
через `asyncio.gather`. Первая безопасная причина сохраняется в `run_quality` и
`Run.error_message` в ограниченном размере.

Классификация выполняется до full-catalog verification: если все запрошенные
сайты (в том числе единственный Pharmonline) завершились `site_fatal`, run имеет
статус `failed`; если хотя бы один другой сайт отдал пригодный результат, общий
run имеет статус `degraded`, сохраняет этот результат и затем fail-closed
останавливается на проверке полного каталога. Не выбрасывать из `__aenter__`
другой startup-тип, который обойдёт `scrape_site`: он отменит peer-задачи и
потеряет уже полученные здоровые результаты.

**HTTP 403 на WebSocket handshake** (наблюдалось 2026-05-27):
- Cloudflare/IPRoyal session ban после high-volume scrape
- Wait 5-10 мин, retry — IPRoyal session rotation помогает
- Если повторяется: `systemctl restart pharmacy-monitor-scrape@pharmonline`
- Если упорно: проверить баланс/доступ paid proxy и DDP reconnect logs; Mac
  launchd не является штатным fallback.

**`ConnectionClosedError: no close frame received or sent`** во время persist phase:
- Это нормально — DDP server тайм-аутит ping pong когда event loop долго блокирован
- `_DDPClient` имеет reconnect-on-close (Phase 1c.4) — auto-recover, retry 1 раз с fresh session
- Если retry тоже падает → check `journalctl -u pharmacy-monitor-scrape@pharmonline`

**Меняем proxy провайдер**:
```bash
# Update /etc/pharmacy-monitor/env on prod (root only)
# IPROYAL_USERNAME, IPROYAL_PASSWORD, IPROYAL_HOST=geo.iproyal.com:12321
# BRIGHTDATA_USERNAME, BRIGHTDATA_PASSWORD, BRIGHTDATA_HOST
# SCRAPER_API_KEY (fallback)
# Restart scrape:
systemctl restart pharmacy-monitor-scrape@pharmonline
```

Priority order in `src/scrapers/base.py`:
1. IPRoyal residential (primary для pharmonline)
2. Bright Data Web Unlocker (secondary, для aptekonline)
3. ScraperAPI default pool (3rd-priority, free tier)
4. Direct connection (fallback)

### Сверка личностей pharmonline

**Когда.** Полный сбор pharmonline отказывает на проверке личностей: в `runs`
статус `failed`, причина начинается с `public_api_identity_proof_failed`
(`PharmonlinePublicAPIIdentityError: … refused persistence`).

Сначала прочитать причину целиком и найти в ней `scheduled_admission=…`: с
автодопуска (раздел «Сбор pharmonline: новые товары допускаются сами, остальное
— ручная сверка») новые товары сбор допускает сам, и до ручной сверки дело
доходит, только когда там стоит `refused(…)` — что именно сбор допускать
отказался, названо в скобках и разобрано в том разделе. Читать в
`runs.error_message` или в `runs.run_quality->>'catalog_verification_reason_full'`:
колонка `catalog_verification_reason` обрезана до 300 знаков, а эта часть стоит
в хвосте и в неё не помещается. Если `scheduled_admission` нет и в полной
причине, допускать сбор не отказывался: либо прогон шёл кодом без автодопуска
(ночной таймер исполняет выложенную копию — `grep -c
_admit_pharmonline_public_api_scheduled_identities
/opt/pharmacy-monitor/src/main.py`, 0 — автодопуска там нет; еженедельный сбор
из GitHub Actions и ручная сверка исполняют `main`, серверная копия о них ничего
не говорит), либо проверка личностей отказала по другой причине — в обоих
случаях ручная сверка.

**Чем.** Два ручных workflow, оба исполняют код своего чекаута из чернового
каталога на сервере, живой каталог не трогают:

1. `plan-pharmonline-decodo-public-api-reconciliation.yml` — план, ничего не
   пишет;
2. `recover-pharmonline-decodo-public-api.yml` — бэкап базы, сверка
   (`--apply`), через полчаса полный сбор. Параметры: `confirmation=RECONCILE`
   и `plan_run_id` — номер успешного прогона плана.

Оба требуют зелёный CI на том же коммите, а второй — ещё и успешный план с
того же коммита.

Оба ходят на сайт через Decodo (`PHARMONLINE_PUBLIC_API_TRANSPORT=decodo`
прошит в файлах; еженедельный сбор с 2026-10-04 ходит `direct`). Если Decodo не
отвечает, план падает с `decodo_request_failed`, и сверку запустить нечем — так
упал план 2026-10-06. Смотреть в журнале шага плана, причина — в строке
`pharmonline_public_api_catalog_rejected`.

**Сверка не мигрирует.** Схему двигает только `deploy.yml`. До бэкапа и до любой
записи второй workflow сверяет ревизию базы с головой миграций своего коммита и
при расхождении отказывает:

```
refusing reconciliation: production DB is at migration <ревизия базы>, this commit's
migrations end at <голова коммита>; deploy this commit with deploy.yml
(apply_migrations=true) first; this workflow does not migrate
```

**Сравнить ревизии до плана.** План их не сверяет и идёт долго — расхождение
всплыло бы только на втором workflow:

```bash
# база
ssh root@13.140.186.143 "sudo -u postgres psql -X -At pharmacy_monitor \
  -c 'select version_num from alembic_version'"
# коммит, с которого собираешься запускать (базу не трогает)
uv run alembic heads
```

Если миграции коммита впереди базы, выходов два:

- выложить этот коммит с миграцией
  (`gh workflow run deploy.yml --ref main -f apply_migrations=true`), потом
  план и сверка с `main`;
- не выкладывать посреди инцидента, а запустить план и сверку с коммита, чья
  голова миграций равна ревизии базы: обычно это последний коммит `main` перед
  непримененной миграцией (`git log --oneline -- migrations/versions`). Ветка от
  него, оба workflow с `--ref <ветка>`. Выложен ли этот коммит, неважно — сверка
  живой каталог не трогает. Workflow при этом берётся тоже с ветки, поэтому
  годятся только коммиты, в которых эта правка уже есть (PR #44): в более ранних
  сверка сама исполняет `alembic upgrade head`.

Отказ «revision cannot be read with this commit's migrations» — `alembic current`
не отработал; почему — в строке Alembic прямо над отказом. `Can't locate
revision identified by …` — обратный случай: база ушла вперёд коммита,
запускать надо с выложенного. Любая другая ошибка — база недоступна или код
коммита не импортируется на сервере, и совет про выложенный коммит тут ни при
чём (сам текст отказа у сверки этого не различает).

**Пока идёт сверка, выкладку с миграцией не запускать** (и в понедельник, пока
идёт еженедельный сбор, — тоже). Ревизия сверяется один раз, до первой записи;
между ней и сбором каталога проходит больше получаса, а группа `concurrency` у
`deploy.yml` своя, так что одно другого не ждёт.

До 2026-10-07 этот workflow сам исполнял `alembic upgrade head` и сверял
результат с прошитой `0021_…`: на голове 0023 он упал бы уже после бэкапа и
миграции, а с коммита с новой миграцией двинул бы схему мимо проверок
`deploy.yml`.

**Что остаётся на сервере.** Каждый запуск, дошедший до сервера, оставляет
черновой каталог `/opt/pharmacy-monitor/.codex-decodo-reconciliation-apply.*` с
исходниками, а если дело дошло до бэкапа — и с копией базы до сверки. Сами
каталоги не удаляются: убирать руками, когда копия больше не нужна. Последний
шаг workflow пишет, что именно осталось.

### Еженедельный сбор pharmonline отказал на ревизии базы

> ⚠️ С правки 2026-10-13 расписания у этого workflow нет — раздел теперь про его
> ручной запуск. Pharmonline каждую ночь собирает таймер сервера из выложенной
> копии, и ревизию базы тот путь так не сверяет.

Понедельничный сбор (`autonomous-pharmonline-decodo-public-api.yml`) исполняет
код `main` из чернового каталога на сервере и до первого обращения к базе
сверяет её ревизию с головой миграций своего коммита. При расхождении шаг
«Run guarded Decodo refresh…» красный, в его журнале:

```
refusing weekly refresh: production DB is at migration <ревизия базы>, this commit's
migrations end at <голова коммита>; deploy this commit with deploy.yml
(apply_migrations=true), then dispatch this workflow again; it does not migrate
```

Причина почти всегда одна: миграцию смержили в `main`, а выкладки с
`apply_migrations=true` не было. Сбор при этом ничего не записал. Выложить
(когда можно — «Обновления / деплой нового кода»), **дождаться зелёной
выкладки** и только потом запустить сбор руками, не дожидаясь следующего
понедельника. Запущенный сразу следом сбор дойдёт до сверки раньше, чем
выкладка применит миграцию, и откажет второй раз:

```bash
gh workflow run deploy.yml --ref main -f apply_migrations=true
gh run list --workflow deploy.yml --limit 1   # ждать: completed, success
gh workflow run autonomous-pharmonline-decodo-public-api.yml --ref main
```

Другие два отказа того же шага:

- `the production DB revision cannot be read with this commit's migrations` —
  `alembic current` не отработал; почему — в строке Alembic прямо над отказом.
  `Can't locate revision identified by …` значит, что база ушла вперёд `main`:
  выложена ветка с миграцией, которой в `main` нет, — смержить миграцию либо
  запустить сбор с выложенного коммита (`--ref`). Любая другая ошибка — база
  недоступна или код коммита не импортируется на сервере: чинить её, совет про
  миграцию тут ни при чём;
- `this commit must have exactly one migration head` — в коммите две головы
  миграций, свести в одну.

## 🕐 Intraday rotation (Phase 5.1c, 2026-05-28)

Ежечасно с 05 до 17 по времени сервера (прод в Europe/Berlin — летом это 03–15
UTC), 13 тиков в день. Тик обслуживает только aloe (`intraday.INTRADAY_SITES`) и
идёт по очереди по top-30 volatile категорий, у которых есть раздел aloe. Между
прогонами на одном сайте не меньше двух часов, поэтому из 13 тиков сбором
заканчиваются 5–7. В журнал алертов тик ничего не пишет: он зовёт `scrape`, а
не `run`.

### Письмо админу о ценах с тика

Решение владельца 2026-10-07: алерты с тиков — только админу.

После сбора категории тик считает локальные ценовые правила (`price_drop_pct`
и `price_change_pct`, если они включены, с их порогами; на проде включено
только первое) по тем ценам, что сам записал, против последней доверенной цены
товара. Что нашлось, уходит одним письмом — и одним сообщением в Telegram, если
он привязан, — получателям с ролью admin/owner. Сотруднику клиента не уходит
ничего, а само событие нигде не хранится: его нет ни на странице `/alerts`, ни
в дайджесте, и ссылка «Открыть в дашборде» из такого письма его не покажет.

Зачем это нужно: цену, которую тик записал первым, недельный проверенный сбор
подтверждает молча, и обычного алерта о таком падении не будет вовсе.

- ⚠️ «Админ» здесь — роль, а не лично владелец. Письмо получит каждый активный
  пользователь с ролью admin или owner, а `admin` — роль по умолчанию у
  `tenant add-user`. У сотрудника клиента должна стоять роль viewer; проверить:
  `select id, role, is_active from tenant_users;`. На 2026-10-07 админ один —
  владелец.
- Порог важности и «тихие часы» админа действуют как обычно. Галочка
  «ежедневный дайджест» письмо НЕ отменяет: в дайджест такое событие не
  попадёт, его нет в базе.
- Сбор категории завершился не `ok` — писем по нему нет.
- Товар без доверенной цены (ни один проверенный сбор его цену не записал и
  не подтвердил) пропускается: сравнивать не с чем.
- Не повторяется: падение, о котором проверенный сбор уже сообщил всем в
  пределах cooldown правила, и товар, у которого цена к оплате с прошлого
  наблюдения не изменилась (snapshot пишется и при смене одной метки акции).
  Между тиками cooldown не действует — событий в базе нет: цена, менявшаяся
  несколько раз и оставшаяся ниже доверенной, даст письмо на каждое изменение.
- Письмо, которое не ушло, потеряно: повторной отправки нет. Так же навсегда
  молчит падение, которое первым записал сбор без права на письмо — тик,
  завершившийся не `ok`, или ручной `scrape`: следующий тик увидит ту же цену
  и сочтёт её уже известной.
- Выключить: снять `is_active` у правила (тогда оно молчит и в полных сборах)
  или поставить админу порог email `off`.

В журнале тика: `alerts_partial_run_local found=N` — сколько событий нашлось;
`intraday_price_alerts_mailed email=… telegram=…` — ушло;
`intraday_price_alerts_failed` — не посчиталось или не ушло (сбор при этом
записан, тик не падает); `intraday_price_alerts_no_recipient` — события есть,
но ни у одного админа они не прошли порог.

### Ежедневный сбор: что стоит на сервере

**Ритм (решение владельца 2026-10-13).** Все три сайта собираются полным
каталогом каждую ночь. Карта — `src/cadence.py`, 24 часа у всех трёх; из неё
выводятся пороги «данные устарели» — 30 часов: health (`site_silent`,
`full_catalog_overdue`, `stale_run`), доверие каталогу и срок жизни
рекомендаций. С 2026-10-06 и до выкладки этой правки на сервер ритм недельный,
и этот документ в других разделах местами говорит «недельный сбор»,
«понедельник», «174 ч» — те строки писались под него; помечены не все.

**Будильники.** У `pharmacy-monitor-scrape@<сайт>.timer` их два, по времени
хоста (Europe/Berlin), случайная задержка до пяти минут:

- 01:00 — сбор. Стартуют все три сайта и идут по очереди под общим замком
  сбора; вся очередь — около 70 минут (pharmonline около 5, aloe и aptekonline
  примерно по 30 — длительности прогонов 2026-10-04…12);
- 03:15 — повтор. Сайт, уже собранный в этом окне ритма, `run` пропускает без
  единого запроса (в журнале `run_skipped_within_cadence`); сайт, чей сбор не
  удался (`failed`, `degraded`), собирается заново.

Окно ритма открывается каждый вечер в 22:00 UTC (02:00 Баку). Ручной сбор днём
по Баку ночной не отменяет. Ручной сбор после 22:00 UTC окно закрывает: оба
ночных будильника сайт пропустят, следующий плановый сбор — через ночь.

**Что на сервере делает root.** `deploy.yml` кладёт `infra/systemd/` и
`infra/scripts/` в `/opt/pharmacy-monitor/infra/` (каталог на сервере есть —
чтение 2026-10-13), но в `/etc/systemd/system` ничего не ставит и оттуда
ничего не убирает. Пока шаги не сделаны, на сервере прежнее расписание.
Смотреть, что стоит:

```bash
systemctl cat 'pharmacy-monitor-scrape@aptekonline.timer' | grep OnCalendar
systemctl list-timers 'pharmacy-monitor-scrape@*'
```

Должно быть: две строки `OnCalendar` (01:00 и 03:15) без `Mon`, у всех трёх
таймеров следующее срабатывание — ближайшей ночью. Шагов два, и они разнесены
вокруг выкладки:

```bash
# ДО выкладки кода ритма: снять недельный drop-in aptekonline. Удаление файла
# из репозитория его из /etc не убирает.
rm /etc/systemd/system/pharmacy-monitor-scrape@aptekonline.timer.d/zz-weekly-cadence.conf
rmdir /etc/systemd/system/pharmacy-monitor-scrape@aptekonline.timer.d
systemctl daemon-reload
systemctl restart pharmacy-monitor-scrape@aptekonline.timer

# ПОСЛЕ выкладки: поставить таймер с двумя будильниками — выкладка положила его
# в /opt.
install -m 0644 '/opt/pharmacy-monitor/infra/systemd/pharmacy-monitor-scrape@.timer' \
  '/etc/systemd/system/pharmacy-monitor-scrape@.timer'
systemctl daemon-reload
systemctl restart pharmacy-monitor-scrape@aloe.timer \
  pharmacy-monitor-scrape@pharmonline.timer pharmacy-monitor-scrape@aptekonline.timer
systemctl list-timers 'pharmacy-monitor-scrape@*'
```

⚠️ Установщик `infra/scripts/install_systemd_schedule.sh` drop-in'ы из `/etc`
не удаляет, а ставит всё, что лежит в `infra/systemd/overrides/` копии в
`/opt`: запущенный ДО выкладки, он вернёт недельный drop-in aptekonline из
прежней копии; запущенный после — недельный drop-in в `/etc` не тронет. Он же
ставит юниты сбора, watchlist и rematch и включает их таймеры — это больше,
чем нужно для смены ритма; на сервере он, по записи в CLAUDE.md, не
исполнялся ни разу. Для смены ритма хватает двух шагов выше.

⚠️ У таймеров `Persistent=true`: после смены расписания перезапущенный таймер
может сработать сразу (поведение systemd; на этом сервере не проверено). Под
кодом с недельной картой такой запуск ничего не собирает, если сайт на этой
неделе уже собран удачно; иначе соберёт сразу. Под кодом с суточной картой это
немедленный сбор, у aptekonline — платный. Поэтому drop-in снимают ДО выкладки
кода. То же со вторым блоком команд (таймер с будильником 03:15, уже под
суточной картой): если сайты в текущем окне ритма собраны — шаг 5 порядка ниже,
сделанный после 22:00 UTC прошлого вечера, — запуск пустой; если нет — все три
сайта начнут собираться сразу.

удачного сбора — запускать его руками незачем, пока ночной сбор исправен.

**Что наблюдать первую неделю.** Наличие товара теперь снимается каждую ночь.

### MCP playbook — install per-project vs user-global

**user-scope** (`-s user`, по умолчанию у нас все 9 MCP): доступны в каждом
проекте Claude, конфиг в `~/.claude.json`. Применяй для personal tooling
(Perplexity, Brave, Firecrawl) и любых key-bearing сервисов которые не
коммитятся в репо.

**project-scope** (`-s project`): конфиг в `.claude/mcp.json` репозитория,
коммитится. Применяй для team-shared MCPs (например внутренний linear MCP
команды, custom company-specific tools).

**local-scope** (`-s local`): только для текущего проекта, в `.claude/mcp.json`
но НЕ под git (gitignored). Используй для experimental или sensitive-but-shared
configs.

```bash
# Установить (3 scope варианта):
claude mcp add <name> -s user    -e KEY=$VAL -- npx -y <package>
claude mcp add <name> -s project -e KEY=$VAL -- npx -y <package>
claude mcp add <name> -s local   -e KEY=$VAL -- npx -y <package>

# Migrate user → project (для team-shared)
claude mcp remove <name> -s user
claude mcp add <name> -s project -e KEY=$VAL -- npx -y <package>
```

### MCP env-var propagation troubleshooting

**Симптом**: tool сразу возвращает `Unauthorized: API key is required` или `403 invalid token`, хотя key верный.

**Корень**: Claude spawn'ит MCP server'а subprocess'ом и передаёт env через `-e` флаги. Если key содержит спец-символы (`$`, `!`, `:`, backslash) — shell может их интерпретировать ДО передачи в `claude mcp add`.

**Диагностика**:

```bash
# 1. Проверь актуальный env у spawn'нутого процесса:
ps -ef | grep <server-name>          # узнать PID
ps eww <PID> | tr ' ' '\n' | grep KEY  # увидеть env vars процесса

# 2. Сравни с тем что в ~/.claude.json:
grep -A5 '"<server-name>"' ~/.claude.json
```

**Фикс**:

```bash
# Используй single-quotes для значения:
claude mcp add foo -s user -e 'FOO_KEY=fc-abc!def$ghi' -- npx -y foo-mcp

# Или экспортируй через temp env-file:
echo 'FOO_KEY=fc-abc!def$ghi' > /tmp/foo.env
claude mcp add foo -s user --env-file /tmp/foo.env -- npx -y foo-mcp
rm /tmp/foo.env
```

## 🧬 Модели и миграции

Схему боевой базы меняют только миграции (`migrations/versions/`), а ставит их
`deploy.yml` с `apply_migrations=true`. При этом `storage.init_db()` зовёт
`create_all` и на PostgreSQL, и зовёт его почти каждая команда CLI: модель, для
которой забыли миграцию, создала бы таблицу в боевой базе сама, а забытая
колонка уронила бы первый запрос к своей таблице.

### Тест красный: «Модели и миграции расходятся»

`tests/test_models_match_migrations.py` (джоба `Test (pytest)`) берёт
замороженную схему ревизии 0023, накатывает на неё миграции чекаута и сверяет
результат с моделями. В сообщении — список: `add_*` значит «есть в модели, нет
в базе», `remove_*` — «есть в базе, нет в модели», `modify_*` — различие в типе,
NULL или серверном значении по умолчанию.

- Меняли модель — нужна миграция: новый файл, `down_revision` — текущая голова.
- Писали миграцию, а список не пуст — она делает не то, что описано в модели
  (другое имя индекса, тип, NULL). Править миграцию, пока она не выложена.
- Снимок `tests/fixtures/schema_baseline_0023.sql` не правят и не пересобирают:
  тест сверяет его контрольную сумму, а пересборка из пустой базы узаконила бы
  любую забытую модель.
- Миграцию, которую уже выкладывали, не правят — нужна следующая.

Одно расхождение тест пропускает намеренно: серверное значение по умолчанию,
которое есть в базе, но не названо в модели (миграция ставит его, чтобы
заполнить уже лежащие строки). Чего тест не видит — в его шапке; главное:
таблицы снимка пусты, поэтому колонка NOT NULL без значения по умолчанию и
заполнение строк пройдут тест и упадут на выкладке, а миграцию, которая
выравнивает боевую базу со списком ниже, снимок не проверит.

Локально тесту нужен PostgreSQL; без него тесты с базой пропускаются, в CI
пропуск считается ошибкой:

```bash
docker run -d --name pm-schema-check -e POSTGRES_USER=pm -e POSTGRES_PASSWORD=pm \
  -p 127.0.0.1:55471:5432 postgres:16
DATABASE_URL=postgresql+psycopg://pm:pm@127.0.0.1:55471/postgres \
  pytest tests/test_models_match_migrations.py -q
```

Просто `alembic check` после `alembic upgrade head` на пустой базе этого не
ловит: миграция `0001_initial` строит схему из моделей самого чекаута, и на
пустой базе модель без миграции создаётся вместе со всеми.

### Чем боевая база отличается от моделей (замер 2026-10-08)

Тест сверяет модели с базой, какой её строят миграции. Боевая строилась дольше
и не только ими. Замер — чтением схемы, без записи: ревизия
`0023_snapshot_confirmed_run`, всё, что нужно моделям, в базе есть — ни одной
недостающей таблицы или колонки. Отличия:

| Что | Где | Откуда и чем грозит |
|---|---|---|
| три лишние колонки и два индекса | `products.normalized_attrs`, `normalized_at`, `normalize_hash` | миграция `0004_product_normalized_attrs` из ветки `claude/infallible-euclid-07bed8` (ИИ-нормализация, май): на прод её ставили, в `main` она не вошла — там после 0003 идёт 0005; колонки допускают NULL, запись не ломают |
| индекс назван иначе, второго нет | `roi_actions_cache`: стоит `idx_roi_cache_computed_at`, нет `ix_roi_actions_cache_tenant_id` | таблицу создала миграция 0005 со своим именем индекса; в таблице по строке на тенант и сайт клиента |
| NULL разрешён, в модели запрещён; нет индекса по тенанту | `scrape_requests` (`tenant_id`, `mode`, `status`, `requested_at`) | миграции у таблицы нет, заведена своим SQL с серверными значениями по умолчанию; ORM заполняет все четыре поля |
| NULL разрешён, в модели запрещён | `matches.needs_review` | миграции у колонки нет; в базе у неё серверное значение `false` |
| `jsonb` вместо `json` | `runs.products_per_site`, `runs.products_per_site_category` | миграции для этого нет; чтению и записи не мешает |
| серверные значения по умолчанию, которых нет в моделях | 31 колонка | у 26 — манера миграций, см. выше; у пяти (`scrape_requests`, `matches.needs_review`) — из того же SQL, которым их заводили |
| таблицы-бэкапы разовых чисток | 21 таблица вида `*_bak_*` и `*_after_initial_*` | не используются кодом; удалять — решение владельца |

Ни одно из отличий не мешает работе. Выравнивать — миграцией и по слову
владельца: это запись в боевую базу. Такую миграцию писать с условием («если
колонка есть», «если индекса нет»): в снимке этих отличий нет, и безусловный
`drop_column` или `create_index` уронит тест уже на `alembic upgrade` — с
сообщением «миграции не накатились на схему ревизии 0023». На снимке условная

## 🧪 Restore drill — verified 2026-05-27

**Recovery scenario**: восстановить frontend после failed deploy (i18n rollback experience).

> ⚠️ **Устарело — на текущем сервере не выполнять (помечено 2026-10-07).**
> Учение проверено только на прежнем Hetzner-сервере. На Contabo архивов
> `frontend-src-pre-*.tgz` нет: шаг 2 сначала удаляет `frontend/src`, а
> распаковывать после этого нечего. Адрес в командах заменён заглушкой
> `<server>` намеренно. Отдельного отката одного фронтенда сейчас нет:
> `deploy.yml` выкладывает бэкенд и фронтенд вместе и откажется работать, если
> ревизии базы прода нет в выбранном коммите. Сломанный фронтенд чинится новым
> коммитом через PR и обычной выкладкой.

```bash
# 1. Find latest pre-deploy backup
LATEST=$(ssh root@<server> 'ls -t /var/backups/pharmacy-monitor/frontend-src-pre-*.tgz | head -1')
echo "Will restore from: $LATEST"

# 2. Restore
ssh root@<server> '
  cd /opt/pharmacy-monitor
  rm -rf frontend/src
  tar xzf '"$LATEST"'
  chown -R pm:pm frontend/src
'

# 3. Rebuild + restart
ssh root@<server> '
  cd /opt/pharmacy-monitor/frontend
  sudo -u pm bash -c "NODE_OPTIONS=--max-old-space-size=4096 pnpm build"
  systemctl restart pharmacy-monitor-frontend
'

# 4. Verify
curl -sSI https://leaddrive.cloud/login | head -2  # should be HTTP/2 200
```

**RTO measured**: ~3-5 минут. Backups создаются автоматически перед deploy через ExecStartPre hook + manual `tar czf` step в deploy скриптах.

## Изолированные личности Pharmonline (изменение 2026-10-16, выпуск ещё не подтверждён)

Полный ответ API и sitemap проверяется до записи. Если у отдельных карточек
сменился родной идентификатор или адрес, сбор сохраняет остальные доказанные
карточки. Старый Product, история цен и связки не переписываются; спорные пары
источника записываются в `pharmonline_identity_conflicts` и
`pharmonline_identity_conflict_variants`. Повтор одной пары обновляет последнее
наблюдение, новая пара добавляет свидетельство к прежнему делу. Частичный сбор
не снимает изоляцию и не пишет цены таких пар.

Успешный сбор с изоляцией заканчивается `degraded`, `catalog_verified=false`.
`run_quality.identity_partition` показывает полный размер источника,
проверенные и изолированные карточки. Только проверенные наблюдения дают цены
для сравнений, рекомендаций, писем и выгрузок. Панель и health показывают
предупреждение об изоляции. Это не полная проверка всех личностей и не сбой
обновления остальных товаров. Исключение при последующей обработке отменяет
финансовую пригодность всего прогона, даже если он заканчивается `degraded`.

Ограничения автоматической изоляции: не более 25 текущих пар, не более 1%
источника и не более 25 нерешённых исторических Products на тенанта. Неполный
источник, чужой тенант, повреждённые свидетельства, нарушение сохранённой нижней
границы или массовые изменения по-прежнему останавливают публикацию целиком.
Такой отказ нужно расследовать, а не повышать лимит для зелёного статуса.

Снятие изоляции требует отдельного проверенного решения о личности товара.
Плановый сбор карточки не переименовывает и дела не закрывает никогда. План
recovery, подготовленный до первой изоляции, нельзя повторно применять как
способ её снять. Не удалять журналы и не менять `identity_conflicted` вручную.
Остальные карточки продолжают обновляться, пока отдельные случаи ожидают
проверки. Пока хоть одно дело открыто и его пара есть в каталоге, каждый ночной
сбор pharmonline кончается `degraded`: сам он из этого не выйдет. Закрывают дела
так, как описано в следующем разделе.

### Закрытие дел изоляции (изменение 2026-10-30, выпуск ещё не подтверждён)

Закрывает дела тот же ручной путь, что и retirement: план
`plan-pharmonline-decodo-public-api-reconciliation.yml` с
`retire_conflicting_identities=true`, просмотр и «давай» владельца, затем
`recover-pharmonline-decodo-public-api.yml` с `plan_run_id` этого плана и тем же
флагом. Код — `src/pharmonline_identity_resolution.py`; журнал решений —
таблица `pharmonline_identity_conflict_resolutions` (миграция
`0027_identity_resolutions`), поэтому сначала обычный `deploy.yml` с
`apply_migrations=true`, потом план на том же SHA.

Каждое решение — разделение, а не перенос истории: цены, наблюдения, пары и
допуски остаются у той строки, для которой записаны. Решений три, у каждого
жёсткие условия; не выполнено хоть одно — дело остаётся открытым, план
небезопасен, ничего не пишется:

- **`retired`** — карточку разделяет прежний протокол retirement v1: новый
  родной идентификатор по прежнему адресу (прежний идентификатор в каталоге
  отсутствует) или прежний идентификатор по новому адресу (прежний адрес из
  каталога ушёл — redirect-доказательство здесь не требуется: дело само
  записано полным каталогом, а разделение ничего не утверждает о
  преемственности). Нужны ровно один прежний допуск, совпадение строгого имени,
  ровно одна пара у дела и никого другого на этих идентификаторах и адресах.
  Старая строка архивируется с историей, для текущей пары создаётся новая пустая.
- **`shadow_archived`** — у адреса две строки: доверенная текущая (сайт называет
  её пару дословно, имя совпадает) и историческая «тень» с родным на вид
  идентификатором, которой нет в каталоге, у которой нет ни одного наблюдения и
  ни одной записи в журналах личностей. Тень архивируется (история и пара
  остаются на ней, в текущие цены она больше не попадает).
- **`current_confirmed`** — дело самой текущей строки закрывается вместе с тенью.

Что смотреть в плане (артефакт содержит только счётчики): `reconciliation_safe=1`,
`identity_conflict_cases` — сколько дел открыто, `identity_conflict_retirements_ready`
и `identity_conflict_shadows_ready` — сколько закроется, `identity_conflict_unresolved=0`
(иначе есть дело вне этих форм — разбирать руками, порог не поднимать).
`identity_conflict_pending>0` значит, что план запущен без флага: без явного
согласия ни одно действие сверки не касается открытых дел.

Решение действует, пока дело в том состоянии, которое оно называет
(`case_last_run_id` и хеш пар). Если тот же товар позже снова изолирован, дело
переоткрывается, прежнее решение остаётся историей. ⚠️ Закрыть переоткрытое дело
v1 уже не сможет: пары дела только добавляются, у такого дела их минимум две, а
v1 закрывает дело ровно с одной парой. Карточка останется изолированной до
решения следующей версии; в запросе ниже такое дело видно открытым. Любое противоречие журнала
(маркер без открытого дела, решение без дела, изменённое поле) останавливает
весь каталог, как и прежние проверки журналов личностей.

Проверка на сервере, только чтение — открыто ли дело сейчас:

```sql
SELECT c.id, c.product_id, c.last_run_id, p.identity_conflicted, r.decision
FROM pharmonline_identity_conflicts c
JOIN products p ON p.id = c.product_id
LEFT JOIN pharmonline_identity_conflict_resolutions r
  ON r.conflict_id = c.id AND r.case_last_run_id = c.last_run_id
ORDER BY c.id;
```

Открыто — `identity_conflicted = true` и пустое `decision`. Приёмка: recover
workflow после записи сам делает полный сбор и требует `ok` с
`catalog_verified=true`; после него в этом запросе нет открытых дел, health
снимает `catalog_identity_isolated`, а на обзоре у pharmonline свежий прогон без
приписки о проблеме.

Откат. До `--apply` ничего не пишется: план читает базу в режиме только чтения.
Запись — одна транзакция `SERIALIZABLE` вместе с retirement; любой отказ
откатывает всё. После фиксации логической отмены нет (как и у retirement v1):
`downgrade` миграции отказывает, пока в журнале есть записи. Вернуть состояние
можно только восстановлением резервной копии, которую workflow снял прямо перед
записью, отдельной проверенной операцией с остановкой сборщиков и учётом более
поздних данных. Цена ошибочного решения без отката: новая карточка начинает без
истории, пары подбираются заново; ничего не удалено.

Чего v1 не делает: не переносит историю (продолжение карточки не доказывается);
не закрывает дело, чья пара ушла из каталога (такое дело `degraded` не вызывает
и остаётся открытым); не закрывает дело с несколькими парами, цепочку смен,
несколько теней у одного адреса и тень с любой историей наблюдений.

Перед выпуском обязательны зелёные CI, включая настоящий PostgreSQL:
конкурирующие писатели, полный откат admissions/дел/маркеров и повтор после
отказа; обновление замороженной старой схемы до текущих моделей. Выпуск — только
обычный `deploy.yml` с проверенным бэкапом. После выпуска проверить несколько
плановых прогонов: свежие проверенные цены, одинаковое число дел при повторе,
отсутствие цен спорных пар и честные счётчики health. До этих наблюдений нельзя
утверждать, что повторяемость эксплуатационных сбоев устранена.
